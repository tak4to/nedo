# 伸び悩みの原因分析と戦略提言（2026-08-30, 第三者レビュー）

対象: `agents/submit/` (geometry.py / packer.py / agent.py)
使用ツール: `tools/`（本レビューで作成。`tools/README.md` 参照）
測定条件: 32シーンプール (`tools/scenes_pool.json`)、同一プロセス内実行、
policy 予算 5.0s / optimize 予算 60s、16並列

---

## 0. 結論（先に4行）

1. **32シーン中32シーンが「探索が候補を出せず、無検証のフォールバックを返して死ぬ」で終わっている。**
   荷物を積み切った例はゼロ。ボトルネックは密度でも探索の質でもなく、**死に方**。
2. **原因は「配置検証の3つ目のゲート（整定判定 `is_placed_safe`）にオラクルが無い」こと。**
   `check_inclusion` と `check_transport_path` は厳密再現したのに、3つ目だけ
   `_footprint_supported`（footprint 100%被覆という二値ヒューリスティック）で代用している。
   これが厳しすぎて、まだ置ける局面で「置けない」と誤判定している。
3. **この1点を直すだけで norm% 17.8 → 25.5（+43%）、積載率 32.6% → 40.7%、
   32シーン中29勝2敗、最悪シーン 1.9% → 10.0%。** 実装は数十行。
4. **7シーンでのA/Bは、この問題のシーン間分散に対して検出力が足りない。**
   これまでの採否判断（level-match の撤回など ±1〜2pt）はノイズと区別できていない。

## 1. 支配的な問題: 3つ目のゲートにオラクルが無い

`env.step` は3つの関門を順に通す（`src/ground_handling/env.py:210-230`）。

| # | 関門 | エージェント側の対応 |
| --- | --- | --- |
| 1 | `check_inclusion` | `geometry.check_inclusion` で厳密再現 ✅ |
| 2 | `check_transport_path` | `geometry.check_transport_path` で厳密再現 ✅ |
| 3 | `place_item`（300ステップ整定後の変位/回転しきい値） | **オラクル無し**。`packer._footprint_supported` で代用 ❌ |

`_footprint_supported` は「footprint の 5×5 サンプル**全点**が支持面（+bridge 1.4cm）に
覆われていること」を要求する。これは静的安定性の条件としては**過剰に厳しい**。
剛体は重心が接触面の内側にあれば倒れないので、100%被覆は不要。

### 実測: 終了原因の内訳（32シーン）

| 版 | `transport` で死亡 | `topple` で死亡 | 積み切り |
| --- | --- | --- | --- |
| 現行 | **32** | 0 | 0 |
| 支持判定を完全に撤廃 | 7 | **25** | 0 |
| COM基準（下記） | 27 | 5 | 0 |

`transport` = `is_valid=False`。つまり**探索が何も見つけられず、`_fallback_action` の
最終手段（コンテナ中央の適当な座標）を返して即死**している。
支持判定を外すと今度は整定で崩れて死ぬ。**現行は片側に振り切れている**。

### 実測: 詰まった局面に合法手は残っている

`tools/diag_stuck.py` で、シーン C が15個で詰まった局面を止め、
**実バリデータ**（エージェントのオラクルではなく `env.validator`）で総当たりした結果:

```
=== C_lookahead1 stopped after 16 steps, status={'is_included': True, 'is_valid': False, ...}
15 boxes, total vol 1.115 (27.8% of container)
grid 0.05m: inside cells 33432, free 24678 (73.8%)
  REAL-VALID: pool0 item15 0.5x0.4x0.4 orn0 at local (0.270,-0.505,1.200) rest_on_z=1.000
  ... (打ち切りまでに15件)
```

**容積の73.8%が空いており、実バリデータが通す配置が実在するのに、
エージェントは「置けない」と判断して自死している。**
これらは `_footprint_supported` が張り出し（オーバーハング）として棄却したもの。

### 修正案と実測効果

`_footprint_supported` を**静的安定性の判定**に置き換える:

1. 荷物中心 (cx, cy) が支持面（+bridge）の上にあること
2. footprint の 7×7 サンプルのうち **60%以上**が支持面に覆われていること
3. 覆われたサンプルの重心が、荷物中心から各半寸法の 35% 以内にあること

（実装は `tools/patches.py:_mk_com`。`com60` = frac 0.60）

| 版 | mean norm% | 積載率 | 最悪 | 32シーン中 勝/負 | 終了原因 |
| --- | --- | --- | --- | --- | --- |
| **現行（base）** | 17.82 | 32.6% | 1.90 | — | transport 32 |
| `W_FLAT=600` のみ | 18.91 | 32.3% | 1.90 | 16 / 8 | transport 31, topple 1 |
| 支持判定なし | 21.30 | 41.1% | 3.00 | 17 / 14 | transport 7, topple 25 |
| COM 40% | 23.57 | 39.9% | 8.02 | 24 / 6 | transport 20, topple 12 |
| COM 60% | 24.11 | 39.7% | 6.25 | 26 / 3 | transport 27, topple 5 |
| COM 75% | 21.39 | 36.4% | 4.71 | 20 / 6 | transport 30, topple 2 |
| **COM60 + `W_FLAT=600`** | **25.47** | **40.7%** | **9.99** | **29 / 2** | transport 23, topple 9 |

再現コマンド:
```bash
cd tools
../.venv/bin/python ab.py --scenes scenes_pool.json --tag base --jobs 14
../.venv/bin/python ab.py --scenes scenes_pool.json --tag c60f --jobs 14 \
    --patch com60 --set p:W_FLAT=600
```

### 本命は物理オラクル

COM基準はあくまで静的近似。**本命は `STRATEGY.md` §2.5 / §4 が当初から想定していた
「PyBullet デジタルツインによる物理検証」**で、これは一度も実装されていない
（`agent.py` に `pybullet` の import が無い）。

- コスト: 自分たちの実測で `env.step` = `0.012 + 0.015 × 積載数` 秒。
  40個積載でも1回 0.6秒 → **8秒予算で上位10候補を実際に整定させて検証できる**。
- 効果: 3つ目のゲートが1・2番目と同じく「厳密」になる。
  `_footprint_supported` の閾値チューニングという議論そのものが消える。
- 実装: 別 `BulletClient` に容器と観測済み荷物を再構築し、候補を warp → 300ステップ →
  変位/角度を `validator.place_item` と同じ式で判定。

## 2. 姿勢選択が偏っている（縦置きの塔ができる）

詰まった局面のレイアウトを見ると、大型スーツケースが**立てて**置かれている:

```
x[+0.170,+0.734] y[-0.671,-0.393] z[0.245,1.000]   # 高さ0.755 = 立てたスーツケース
x[+0.168,+0.733] y[-0.074,+0.210] z[0.487,1.246]   # 高さ0.759 = 同上
```

スコア式（`packer.py`）は
`W_BACK(200)·y_back − W_LOW(400)·bottom − W_FLAT(100)·fz − …`。
縦置きは footprint が小さいぶん「より奥・より低い」着地点に届くので、
`W_FLAT` の 100×0.48 ≒ 48点のペナルティを簡単に上回ってしまう。

縦置きの塔は (a) 上に何も載せられず断片化を生む、(b) 重心が上がる（cog_score）、
(c) 揺らすと倒れる（stability_score）——3つの指標すべてに悪い。

`W_FLAT=600` で 32シーン中16勝8敗の +1.1pt、COM60と組み合わせるとさらに +1.4pt。
**重心・安定性スコアへの効果は別途あるはずで（未計測）、実際の価値はこれより大きい。**

## 3. 測定・意思決定プロセスの問題

### 3.1 7シーンでは検出力が足りない

シーンごとの Δnorm% の標準偏差を実測すると **2.9pt（W_FLAT変更）〜7.9pt（支持判定撤廃）**。
n=7 なら平均差の標準誤差は **1.1〜3.0pt**。

つまり `WORKLOG.md` に記録されている以下の判断は、**ノイズと区別できていない**:

- level-match（グローバル版・ローカル版）の撤回: −1.3pt
- wall-building の「中立」判定
- GRASP多スタートの「効果ゼロ」

貪欲法は初手の違いが最後まで伝播するカオス系で、1シーンの結果は本質的に不安定。
**採否は最低30シーン、できれば50〜100シーンで、勝敗数と平均差の両方を見て判断すること。**
32シーンは1構成あたり2〜3分で回る（`tools/ab.py --jobs 14`）ので、コストは問題にならない。

なお `bigfirst` は本物だった: `W_ITEM_VOL=0` にすると 32シーンで −2.6pt、**2勝12敗**。

### 3.2 終了原因を集計していない

これが最大の見落とし。`status` を集計すれば「32/32が探索の自死」は初日に分かった。
`fill_score` だけを見ていると、**なぜ止まったのかが永久に見えない**。
今後はどの実験でも終了原因の内訳を必ず出すこと（`tools/harness.py` が出力する）。

### 3.3 ローカルの fill_score は本番と系統的にずれている可能性が高い

`inclusion_margin` を README 記載の本番値 −0.005 と、`Evaluator` の既定値 +0.02 の
両方で計算した結果:

| | strict (−0.005) | loose (+0.02) | 比 |
| --- | --- | --- | --- |
| 32シーン平均 fill | 12.79 | 22.24 | **1.74倍** |

README は「内包判定は検証時よりも緩く設定されている」と明記しており、
`Evaluator.__init__` の既定値も `+0.01`（`env.py` が validator の値で上書きしている）。
**本番が緩いなら、床接地層が計上され、ローカルの数字は真の性能を4割以上過小評価している。**

影響は単なるスケールではない。**strict 基準は「床に接する配置」を無価値と評価するので、
床面を広く使う戦略が不当に低く見え、逆に縦積みの塔が有利に見える**。
§2 の姿勢の偏りは、この評価バイアスに部分的に誘導された可能性がある。

→ 今後は `fill_loose` を併記し、**採否は両方が同方向のときのみ**とすること
（`tools/harness.py` が両方出力する）。`FLOOR_LIFT` で床から浮かせようとする
努力はどちらの前提でも報われないので、優先度を下げてよい。

## 4. 最大の戦略的見落とし: fill_score 以外の4指標

README の最終スコアは**5項目の加重平均**（`README.md:379-386`）。
README が示すフィードバック例は:

```json
{"fill_score": 15.31, "cog_score": 66.84, "stability_score": 72.07,
 "placement_score": 80.0, "soft_item_score": 100.0, "num_placed_items": 1.0}
```

ここから読み取れること:

- **`fill_score` は構造的に最も伸びない項目**。理論上限が65点前後で、実力値は15〜30点。
  一方 cog / stability / placement / soft は **0〜100 のフルレンジ**で、しかも
  例では 67 / 72 / 80 / 100 と高い値が出ている。
- **`num_placed_items: 1.0`（全積み）でも fill_score は 15.31 にしかならない。**
  つまり fill_score を追いかけても、加重平均への寄与は上限で頭打ちになる。
- **これまでの作業は 100% が fill_score に費やされ、残り4項目は一度も測っていない。**

さらに深刻な未確認事項が1つある。README の
「手荷物を**一定数以上**積載できていないと充填率スコア以外は0となる」という条項。
**現状の積載率は32%。この閾値を下回っていれば、5項目中4項目が0点。**
それが「思った以上の結果が出ない」ことの最も単純な説明になる。

### やるべきこと

1. **積載率（`num_placed_items`）を第一目標に切り替える。**
   `fill_score` ではなく積載個数を最大化する。`choose_action` の `W_ITEM_VOL`（大物優先）は
   体積を稼ぐ設定であり、**個数を稼ぐ設定とは限らない**。両方を測って選ぶこと
   （`tools/harness.py` は `pct` として積載率を出力する）。
2. **提出をプローブとして使う。** 1日5回・最終2ファイル。
   意図的に構成を変えた提出を並べ、返ってくる cog / stability / placement / soft の
   値の動きから、閾値と重みを推定する。例:
   - (a) 現行版
   - (b) COM60 + W_FLAT=600（積載率 +8pt）→ 閾値を越えたかが `cog_score` 等の
     0/非0 で分かる
   - (c) 意図的に軽い荷物を上・重い荷物を下だけ変えた版 → cog_score の感度が分かる
3. **4指標のローカル代理を実装する。**
   - cog: 重心高さ（`tools/harness.py` に `cog_h` として実装済み）
   - placement / soft: 優先手荷物・ソフト貨物の「異種による埋没数」
     （同上 `n_prio_buried` / `n_soft_buried` / `n_prio_wrong`。現在ほぼ0だが、
     積載率が上がると必ず増える）
   - stability: `Container.create_cap()` は**ローカルでは未使用**。
     蓋をして重力方向を振る自前テストを書けば代理指標になる（README の
     「コンテナを揺らした際に」に対応）。

## 7. 補足: `_fallback_action` の最終手段について

現在、探索が空振りすると `_fallback_action` はコンテナ中央の適当な座標を
**無検証で**返す（`agent.py:88-95`）。コメントは「どのみちエピソードは終了する」と
説明しているが、これは正確ではない。
**3つの関門をすべて通る手を返せれば、エピソードは続く。**
32/32 がここで死んでいる以上、最終手段は「諦めの座標」ではなく
「もっと必死に探す」であるべき（細かいグリッド、全姿勢、支持判定の段階的緩和）。
施策1はこの経路そのものを改善する。
