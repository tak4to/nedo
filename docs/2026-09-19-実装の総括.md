2026-08-30 〜 2026-09-19 の全作業の統合版。個別の詳細は `docs/` 配下の日付つき文書と
`WORKLOG.md` に残っているが、知識が10本以上に散っているのでここに一本化する。

## 1. 効いたもの

### 1.1 計算資源の配分（最大の単一改善、LB +26）

`choose_action` が policy 予算を `pool × containers` で**均等割り**していた。
`look_ahead=20` だと 3.5秒÷18 = 0.19秒/回に対し `best_placement` は半分埋まった
コンテナで 0.25〜0.35秒必要。**全部タイムアウトして「何も置けない」と報告して自死**
していた。その局面を3cmグリッドで全探索すると **13543件が受理される**。

`MIN_CALL_BUDGET = 0.8`（1回最低0.8秒を保証、余らなければプール末尾は評価しない）:
dev **+2.37**、ホールドアウト **+2.27**。floor を 0.4/0.8/1.5/2.5 で振ると
+1.76/+2.37/+1.71/+2.21 で 0.8 が膝。**効いているのは floor であって順序ではない。**

派生: `_landing` の 4.81倍高速化（箱をタプル化＋天面降順で早期打ち切り、
90000クエリで意味論完全一致）: dev +0.44 / hold +0.45。`best_placement` の46%を
占める最内ループだった。

**修正後は計算資源はもう律速ではない**: 予算を3倍(15秒)にしても **+0.07**
（改善前は +2.78）。

### 1.2 `SUPPORT_LIFT < GAP` — 単一定数13mmの修正（積載率 42%→59〜62%）

`packer.SUPPORT_LIFT = 0.017` に対し `geometry.GAP = 0.022`。棚や危険帯の上に置くとき
8cmリフトが0になるので掃引が荷物自身の高さを通り、支持面との距離は持ち上げ量そのもの。
`check_transport_path` は GAP 以下を衝突と見なすため、**この経路の配置が例外なく不正**
だった。詰まり局面で棚上 187箇所中 **0 → 40箇所**が有効に。

スイープ 0.026/0.030/0.035/0.040 で +14.8/+16.2/+16.3/+15.8 とプラトー、**0.030 採用
（32勝0敗）**。再発防止のためコードでは `SUPPORT_LIFT = GAP + 0.008` と GAP から導出する形にした。

**教訓: 設計クリアランス定数が、バリデータの要求する安全マージン(`GAP`)を下回って
いないか全部確認すること。この種のバグは例外を出さず、静かに候補を全滅させる。**

### 1.3 CEM full14 — 同時最適化でしか到達できない領域がある

新特徴量7個を重み0で追加し、既存7重みと合わせた**14次元を CEM で同時最適化**。
未使用96シーンで composite **+6.34**（se 0.54, t=11.6）、84勝12敗、積載率 +5.75pt。
訓練 +7.67 に対し未使用 +7.68 で**転移がほぼ完全**。

決定的なのは比較対象: **既存7重みだけの CEM（base7）は訓練 +3.50 / 未使用 −0.87 で失敗**。
そして**追加した特徴量群は、1項ずつの単独A/Bでは 0勝24敗だった**。

**教訓: 新しい判断基準は、単独A/Bで却下する前に「重み0の特徴量」として足し、CEMに入れる。**
効果が無いのではなく、他の重みがその項の存在を前提に調整されていないだけのことがある。

**仮説が外れた符号（人間の直感なら3つとも逆に振っていた）**:
`W_SEAM` は負＝継ぎ目を**揃える**方が良い（インターロック仮説と逆）、
`W_SOFT_DEFER` も負＝ソフト荷物は**先に**置く方が良い、`W_ITEM_VOL` は半減。

### 2.2 探索を広げる系（5連敗、全て同じ理由）

| 手法 | 結果 |
| --- | --- |
| GRASP ランダム再スタート200本 | 40シーンで固定4キーと**全シーン完全一致**。135秒を消費 |
| `OFFLINE_RESTARTS` 8本の独立ウォーク | composite −0.32（se 2.48, 4勝4敗）、シード間の散らばりが 3.68→4.70 と**増加** |
| プレフィックスキャッシュ | 予算を使うが払わない |
| 単に長く探索する | 予算3倍で **+0.07** |
| プール予算の2パス化 | 大プールで −0.73 / −0.49 |

**全て同一の理由**: ロールアウトは同一シーンの2順序を **Spearman +0.49** でしか
並べられない。このノイズ下で候補N本の最大を取ると、**最も楽観的に間違えた候補**を
引く確率が真の最大と同じ速さで増える（optimizer's curse, Smith & Winkler 2006）。

**系**: この忠実度では追加の探索は何も買わない。**払った2つの変更はどちらも
「候補数」ではなく「順位付け」を改善した**（`OFFLINE_TIEBREAK` と `ROLLOUT_SETTLE`）。

### 2.3 物理シミュレータを判定器に使う系（3形態すべて失敗）

`twin.py` は**実崩落を 12/12 検出**する精度がある。にもかかわらず:

| 使い方 | 結果 |
| --- | --- |
| 拒否権 | dev +0.45 / hold **−0.77** |
| 選好（降格のみ） | dev +0.30 / hold −0.35 |
| 二段選抜の判定器（3変種） | 上位3本からの選抜で −0.80 / −0.62 / −0.21（全敗） |
| stability への影響（09-19） | 38.06 → **37.40**（動かさない） |

**転倒は詰まりの原因ではなく症状。** 最良の配置が転ぶ局面では、コンテナは既に
終わっている。拒否しても死に方が変わるだけ。

**さらに方法論の誤りが1つ**: 二段選抜の合否基準に ρ を使ったが、settle 300版は
**ρ 0.444 で事前宣言した基準を超えたのに実益は −0.21**。ρ は候補集合**全体**の
順位相関で、選抜が問うのは**上位数本の識別**だけ。
**選抜タスクの評価指標は、選んだ結果の実現値。**
（同じ ρ がサロゲート改良の指標としては正しく働いた。同じ量が用途によって
正しい指標にも誤った指標にもなる。）

### 2.4 look-ahead / 再ランク系（09-19 に決着）

- **A-4 feasibility counter**: W_FEAS 100/500/2000 で 48.42/48.93/48.53（baseline 48.88）。
  1651回の判定を計装すると、**上位3候補の feasibility 差が88%のケースで厳密にゼロ**、
  判定が変わったのは 0.8%。
  → 高さマップが測るのは**頭上の余裕**だが、束縛しているのはそこではない。
  `diag_void.py` が既に測った通り**スカイライン下の占有率は85〜93%で、空きの大半は
  スカイラインより上**。使えない理由は「低すぎる」ではなく「届かない」。
  → **A-4は万力に挟まれている**: 安い版は非拘束な量を測り、正確な版（validatorプローブ）は
  予算の55%を食って純損（`survival.py`、25.47→25.31）。
- **上位K再ランクという手法自体**: 同じ計装で**上位3候補の57%が完全に同じ (x,y,z)**、
  distinct は平均1.65/3。**再ランクの対象が物理的に同一**なので何を当てても動かない。
  → これは §2.3 の物理ツイン選好の失敗、`survival.py` の失敗、`stage2_probe.py` の
  3変種全敗を、**単一の理由で説明する**。

## 3. 方法論の教訓（最も移植価値が高い部分）

### 3.1 差が出ないときは、アルゴリズムより先に測定系を疑う

測定基盤のバグを3件踏んだ（§1.6）。どれも「差が出ない / おかしな差が出る」という形で
現れ、アルゴリズム側を疑って時間を溶かす類のもの。

### 3.2 A/Bのばらつきは100%が探索シード雑音で、処置の異質性はゼロ

10シーン × 4探索シード × 2アーム = 80ラン で `d_ij = τ + b_i + e_ij` を分解:

| 成分 | 分散 | sd |
| --- | --- | --- |
| `Var(e)` 探索シード | **35.45** | **5.95** |
| `Var(b)` 真の処置異質性 | **0.00** | **0.00** |

**帰結が3つ**:
1. **検出力に下限は無い。** se は総ラン数だけで決まり、**シーンとシードは等価**。
   32×1 = se 1.05 / 64×4 = **0.37**
2. **過去24件の却下は se≈1.05 で下された。+1.0 に対する検出力は 17%。**
   「効果が無い」と「見えない」は区別できていない
3. 「どのシーンで効くか」を探す分析は原理的に無意味（シーン記述子10個での効果回帰も
   leave-one-out R² = −0.31）

**報告は「+1.68」ではなく「+1.68 (se 0.63, MDE 1.8)」と書く。**

### 3.3 ローカル→LB の換算率は一定ではない（施策の性質で変わる）

| 区間 | 合成プール Δcomp | 実タスク Δcomp | LB 実測 | プール→LB | 実タスク→LB |
| --- | --- | --- | --- | --- | --- |
| B→C（09-06） | +6.34 | +2.26 | **+1.72** | 0.27 | 0.76 |
| 棚下開放（09-21） | +0.66 | +0.40 | **+0.50** | **0.76** | **1.26** |

**長らく「ローカルは2〜3倍 過大評価する」と考えてきたが、棚下開放では逆に
ローカルが過小評価した。**事前予測は換算率0.27〜0.76から +0.18〜+0.30 だったが、
実測は **+0.50** で予測の1.7〜2.8倍。

**この差の説明として最も整合的な仮説**: B→C は全体に効く変更で、飽和した指標
（閾値を越えた後の fill）を押していた。棚下開放は**最弱セグメント（棚あり）に
集中した変更**で、そこは飽和していない。つまり換算率は定数ではなく、
**「その施策が押している指標・セグメントが飽和しているかどうか」**で決まる。

**How to apply:** ローカル値からLBを予測するときは、単一の係数を当てるのではなく
「この施策はどのセグメントを押しているか、そこは飽和しているか」を先に問う。
飽和領域を押す施策は目減りし、未飽和セグメントを押す施策はそのまま乗る可能性がある。
どちらにせよ**絶対値の予測には幅を付けて報告する。**

### 3.4 相関を因果と取り違えない（介入は観察とは違う）

801個の荷物の観察で「側面接触のある荷物は動きにくい」（変位 0.104m vs 0.165m）と
**相関**が出た。これを `W_SIDE` として方策に**介入**として入れたところ、
側面接触を追って積載数が落ち構造が疎になり、**平均変位はむしろ増えた**。

### 3.5 外部事例の効果量は「その実装が抱えていた病気」とセットでしか転移しない

同型コンペの参加者（public 61.092）が corridor_penalty で +2.33 を得ていたので移植したが、
こちらでは4重み単調悪化。**彼らは `fail_transport_y` を22.5%抱えていたが、こちらは
同じ病気を既に構造的に治していた**（`SUPPORT_LIFT` 修正 → A-1ラダー）。
治った患者に薬を足すと、正常な配置を歪めるだけになる。

**外部の効果量を引くときは、その効果が埋めていた穴がこちらにも空いているかを先に確認する。**

### 3.6 「制限」ではなく「追加」の形にする

候補生成を制限する変更は退行リスクを伴う（#5 のY候補制限が 22.9→19.3）。
既存候補への追加にすれば、無効な候補はオラクルが落とすので**構造的に悪化しない**。
A-1のラダーも A-5 の候補点も、この形だから安全に入れられた。

### 3.7 最適化を回す前に、目的関数の1シーンあたり感度を測る

CEM base7 の失敗は事前に防げた。崖の近傍（積載率40〜52%）にいるのは32シーン中わずか6件で、
1件跨ぐと目的値が0.67動く。訓練の +3.50 はその6件中約5件を跨がせたのと同じ大きさ
— **CEMは方策を改善したのではなく、訓練セットのどのシーンが境界上かを記憶した。**
階段関数を直接最適化した時点で必然だった（現在はロジスティック傾斜に置換済み）。

### 3.8 大きくLBを動かしたのは全て構造的な修正だった

27→53 は計算資源の配分、53→55 の主因は定数バグ修正、55→56 は救済ラダー。
**重み調整が単独でLBを動かした証拠は一度も分離して取れていない。**

## 4. 現在の状態

**指標の内訳**（32シーンプール、policy 5.0s / optimize 15s）:
fill 35.5 / cog 53.2 / **stability 38.1** / placement 93.8 / soft 94.0、積載率 62.5%。

stability の幅は **35.6〜38.9 の3.4点**しかなく、どの knob も stability の変化量より
fill/place/soft の劣化量の方が大きい。一方**シーン間**では 18.4〜51.6（sd 6.22）と
よくばらつき、**r(stability, 積載率) = 0.56**。
→ **stability を上げる方法は「もっと積む」ことであり、それは既に最適化している目的そのもの。**
「stability対策」という独立した仕事は存在しない。

**したがって残っている道は、構造的に積載数を上げることだけ。**
placement 93.8 / soft 94.0 は天井近く、stability は従属変数、fill は閾値の上では
頭打ち気味 — という状況で、A-1（LB +1）が示した「詰まりを構造的に潰す」系統が
唯一実績のある方向である。

**未着手で残っている候補**: C-1（課題B/C への8秒ミニLNS移植。課題B の composite 53.71、
棚ありセグメントの積載率 49〜51% が全体最弱）。
