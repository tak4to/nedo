# LB 60 到達計画 — v3（最終案：DS・現場レビュー各2巡を反映）

## Context

- 現状 LB **56.77**（`agents/submit.zip`）、目標 **60**（+3.23）。締切 10-19（残り23日、1日5提出）。書類 10-26。
- 採点 = 足切り（一定数以上積めないと fill 以外0、README:386）＋5指標の加重平均。跨ぎ1本 ≈ +2.3〜2.75（暫定は約25〜35シーン）。
  最終順位は**残りのシーン**で決まり、選択2ファイルの高い方が採用（`docs/comp_determin.md`）。
- 09-25 戦略は「+1.2個/シーン」。しかし再解析で、**ローカル128本では先方に大勝（期待跨ぎ 93 対 56）なのに LB は −4.3**、
  かつ直近4回の LB 差はどれも跨ぎ1本分に届かない → **本番の不合格は「閾値のわずかに下」ではなく「ずっと下（早期終了）」の可能性**。

## 施策（実施順）

### Phase A 即死の除去（09-26〜09-29）— 最優先・下振れゼロ
- **作業前に `agents/submit` の現状をコミット**（`agents/dev` は約450行ずれ・未追跡なので、以降の版は submit から作る）。
- **A-1 buffer 修正**: geom に物理床 `floor_z = thickness + buffer` を追加し、物理的な着地・内包に関わる箇所
  （`packer.py:390, 497, 657, 738, 799, 836, 1156`、`agent.py:242`）をこれに置き換える。
  `floor_struct_z` は検証器の癖（`validator.py:104`、床の着地判定は buffer を含まない）を写す `resting_eff_start_z` 専用に残す。
  buffer=0 では `x + 0.0 == x` で**ビット単位で同一**。
- **A-2 期限の安全網**: `_collect` の列挙ループに期限チェック（N 候補ごと）を入れ、policy 全体に壁時計の硬い上限（6.5s）を置く。
  通常のシーンでは発火しない＝挙動不変。
- **A-3 stress 集合**（`tools/scenegen.py` に生成器を追加、現場レビュー仕様）:
  - コンテナ: buffer {0, 0.005, 0.01, 0.02, 0.04}、厚み 0.02–0.05、L 1.56–2.44 / W 1.19–1.53 / H 1.14–1.63、cut_x 0.30–0.88 / cut_y 0.30–0.65、棚有無×H、台数 1–4、優先コンテナ 0–1、型の混在
  - 既積み: 容積 0–40%、奥の床／扉側、一部傾き・属性付き
  - 荷物: カタログ±20% に小物20–50%、長尺（ゴルフ 1.2–1.35 m、ベビーカー 0.9–1.1 m、スキー 1.6–1.9 m）、質量 2–32 kg、ソフト 10–80%、優先 0–30%
  - 流れ: k {1,3,10,20,40} × max_space {1, k/2, k}、大物後半・優先固まり・ソフト先頭
  - **即死判定**: 例外、6.5s 超の手、**空き容積 50% 超で詰まり終了**。実物理（`tools/harness.py`）で回す
  - 予想弱点の確認: 3–4台×k≥10 の飢餓（0.8s 床×大きい順で約4組しか見ない）、置けない長尺（optimize では順序の末尾へ）、扉側の既積み
- 見つかった即死モードは最小差分で修正（候補を**削らない**形で）。
- **提出①（09-27〜28）**: submit + A-1 + A-2。検証 = ローカル128本で行動列が現行と一致（buffer=0）、buffer=0.01 の stress で個数回復、preflight。
  見つかった追加修正は**提出②**にまとめる。
- 規約: これは文書化された設定値へのバグ修正であり、LB の結果から本番の構成を推し量ることはしない。

### Phase B 測定系と決定化（09-28〜10-01）
- **B-1 仕事量ユニット**: `MAX_VALIDATIONS` は検証回数しか数えず `_landing`（時間の46%）と `_collect` を含まない →
  最内ループで走査する箱数を数える。時計分岐をすべて置換（`choose_action` の per_call・`MIN_CALL_BUDGET`、ラダー、optimize の opening_end・per_trial・avg_trial×1.15・再始動・rollout 打ち切り）。
  合格: policy 1回の「時間÷ユニット」の変動係数 <15%（1–4台・k≤40・多様寸法）。
- **B-2 予算と安全網**: 下限 = 現行ローカル（15並列・5.0s）と同じ計算量（全定数がこの水準で調整済み）、上限 = 本番速度の下限×6.0s。
  段別の安全網: 主探索は壁時計 4.3s で打ち切り、ラダーには 6.5s まで必ず残す。optimize は最重シーン基準、170s で最良順序を返す。
- **B-3 D0 版の合格条件**: 現行比で期待跨ぎ本数が劣らない＋**行動列が 1並列と15並列で一致**。
- **B-4 KPI（`tools/ab.py`・`cmpc.py` を拡張）**: 主検定 = Σ[F(c_B) − F(c_A)] の順列検定（F は事前登録した閾値事前分布 pct U[50,65] と count U[25,33] の等混合の CDF）。
  区分ごとは「有意な悪化なし（片側10%）」。施策は束で検定→分解、施策間 Holm。**事前分布は LB に合わせて選び直さない**。
- **B-5 開発集合**: 異なるシーン512本（公式7種類＋多様寸法 0.2/0.35/0.5＋stress 由来の別寸法コンテナ）。1アーム約1.5〜2時間（15並列）。Phase C は終端フォークで256本・0.3〜0.5時間。
- **B-6 計装（既定OFF）**: 手ごとに到達段・評価品目数・所要・上位K候補の残り高さ r・終了原因・違反の発生源。
- **B-7 再解析（計算ゼロ）**: 却下済み24件（`ab_TW*`、W_SLIVER、S2、CEM 系）を B-4 で再採点、FDR 補正、残ったものは決定化後に再測定。
- **提出③（09-30〜10-01）**: D0（提出①②＋決定化＋予算6.0s）。

### Phase C 救済ラダーの構造修正（10-01〜10-04）
- **C-1 関門 = 終端フォーク**（`tools/diag_stuck.py` 拡張）: 行動の再生で終了直前を復元 → 全品目×全段×細格子を時間無制限で探索（実バリデータ）→ 救済できたら通常方策で続行。
  **詰まり終了1シーンあたり +0.5個未満なら中止**。段ごとに 成功率・連鎖個数・失敗時の損害（押された隣は戻らない）を測る。
- **C-2 実装**: 段の順は強→弱のまま（Lv3 直行は先方で −2.35）。段間の候補共有、主探索とラダー共通の検証結果キャッシュ、
  重複排除（寸法・soft・prio・mass）、段内は最小辺の小さい順、段ごとの最低予算。Lv4 は C-1 で「連鎖ほぼ0かつ損害正」のときだけ外す。
- **C-3（同梱）違反の減点化**: 救済の `relax=True` を「クラス制約の除外」→「質量に比例した違反の減点」に。候補集合は同一。
  課題A の rollout も `_collect` の relax 分岐を通る点に注意。`W_SOFT_DEFER` の符号は変えない（高所のソフトは沈んで転倒）。
- **提出④（10-04）**。期待 +0.4〜0.7（関門通過確率込み）。

### Phase D 最終段合わせ＝縦の死に高さ（10-02 関門判定、10-04〜10-08、最大2案）
- **D-0 関門 = 避けられたか**: 帯の1段目を決めた手で、スコア差 δ 以内の上位候補に死に高さを作らない候補があった割合（B-6 のログから）。低ければ中止。
- **D-1 式**: r = その場所の天井（棚下は棚下面−GAP、他は z_hi）− **落下後の**天面。死に高さ = 0.01 < 帯の余り < プール内最小辺 + 0.04
  （経路に GAP+CEILING_MARGIN ≈ 0.041 必要）。帯の余りは直近20個の辺の部分和（最大4段・1cm刻み）で作れる段積みの最大値を引いた残り。
  通常候補と棚下候補に同じ関数。天井押さえの立て積みは床か棚に直接立つ列で物理隙間 ≤0.06 m のときだけ W_FLAT を緩める。カタログ定数は使わない。
- 事前確率は低い（再ランク型は過去 0/24）。束検定で全区分悪化なし＋帯内プラスのときだけ採用。**提出⑤（10-09）**。

### やらないこと
1台ずつ仕上げる（候補の制限）／棚下の期限ボーナス／救済段の順の入れ替え／`W_SOFT_DEFER` 反転／優先手荷物を扉側へ／総括 §2 と 09-25 §8 の閉鎖済み全件。
