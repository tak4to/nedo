## 0. 結論（先に3行）

1. **勝負を決めるのは「密度の最適化」ではなく「1手も失敗せずに全荷物を積み切ること」**。
   1手でもNGが出るとエピソードが即終了し、そこまでの状態で採点される。
2. シミュレータの合否判定は**完全に決定論的な幾何計算**であり、エージェント側で**厳密に再現（デジタルツイン）できる**。
   これを「実行可能性オラクル」として持てば、無効手を原理的にゼロにできる。
3. その上で **オフライン=ビームサーチ＋LNS、オンライン=スラブ（壁）構築＋オラクル付き貪欲** を積む。
   物理シミュレーションも1ステップ 0.01〜0.6 秒で回るので、**8秒の思考時間内で本物の物理検証まで可能**。

## 1. 問題の定式化

横空きULD（LD3/AKE相当）コンテナへの **オンライン3D積付問題（Online 3D-BPP）** に、
以下の実務制約が乗ったもの。

| 制約 | 内容 |
| --- | --- |
| 押し込み搬入 | 開口部（Y=-W/2）から目標Yまで直進 → 目標Xへ横移動。経路上に障害物があると失敗 |
| クリアランス | 経路上で他荷物・棚と **1.5cm 以内に近づいたらNG** |
| 姿勢 | 6通りの軸平行姿勢のみ（連続回転なし）→ **離散最適化になる** |
| 物理 | 配置後300ステップの整定。0.3m以上ずれる/45度以上回ると失敗 |
| 情報 | 課題Aは全荷物既知・順序のみ決定、課題Bはk個プール、課題Cは1個ずつ |

**重要な構造的特徴**: 荷物は**7種類の固定カタログ**（`configs/item_params.xlsx`）からしか出てこない。
寸法は既知の離散集合なので、**事前に最適パターンを計算して提出物に同梱できる**。

| 種類 | L×W×H [m] | 質量 | soft |
| --- | --- | --- | --- |
| スーツケース大 | 0.75×0.56×0.27 | 18 | - |
| スーツケース中 | 0.65×0.45×0.25 | 13 | - |
| スーツケース小 | 0.55×0.40×0.24 | 8 | - |
| ダッフル/ボストン | 0.60×0.30×0.25 | 7 | ✓ |
| 段ボール | 0.50×0.40×0.40 | 10 | ✓ |
| 大型リュック | 0.65×0.35×0.23 | 12 | ✓ |
| 小型デイパック | 0.45×0.30×0.20 | 5 | ✓ |

## 2. シミュレータ厳密仕様（ソース読解＋実機検証済み）

サンプル AKE: `L=2.0, W=1.45, H=1.61, t=0.04, buffer=0, cut=(0.44, 0.40)` → 有効容積 **4.007 m³**

### 2.1 内包判定（`check_inclusion`）

7枚の平面すべてについて `n·(pos - p) + |n|·half ≤ inclusion_margin` （評価基盤 margin = **-0.005**）。
つまり **全方向に5mm以上内側**でなければならない。実測した平面（サンプル値）:

| 面 | 法線 | 代表点 | 条件 |
| --- | --- | --- | --- |
| 床 | (0,0,-1) | z=0.04 | `z-hz ≥ 0.045` |
| 右壁 | (1,0,0) | x=0.96 | `x+hx ≤ 0.955` |
| 天井 | (0,0,1) | z=1.57 | `z+hz ≤ 1.565` |
| 左壁 | (-1,0,0) | x=-0.96 | `x-hx ≥ -0.955` |
| 斜めカット | (-0.6727,0,-0.7399) | (-0.96,0,0.4177) | 左下隅の面取り |
| 開口(手前) | (0,-1,0) | y=-0.725 | `y-hy ≥ -0.720` |
| 奥壁 | (0,1,0) | y=0.685 | `y+hy ≤ 0.680` |

→ **実効の直方体空間は x∈[-0.955, 0.955] (1.91), y∈[-0.720, 0.680] (1.40), z∈[0.045, 1.565] (1.52)**

### 2.2 搬入経路（`check_transport_path`）— ここが全て

```
x_min = -L/2 + t + cut_x + hx + 0.01      # 扉は左側 cut_x 分だけ狭い
rel_x = clip(target_x, x_min, x_max)
eff_start_z = 0.08                         # 既定の持ち上げ量
  if 底面 z が [床上面, 床上面+0.05] または [棚上面, 棚上面+0.05] → eff_start_z = 0
  elif 上面 z が 棚下面/天井 に近い → eff_start_z = clearance - 0.0185 に縮小
経路: (rel_x, -W/2, z+eff) → (rel_x, y_t, z+eff) → (x_t, y_t, z+eff)
判定: 全サブステップで packed_items / 棚 と距離 > 0.015
```

ここから導かれる**設計上の法則**:

* **(L1) 縦積みはタダ**。経路は最終高さより8cm上を通り、着地の接触は判定されない。
  → 上下に隙間を空ける必要がない（実測: 2mm隙間で6層積み成功）。
* **(L2) X方向の隣接・Y方向の前後は 1.5cm 以上の隙間が必須**。
  最終位置も経路の一部（fraction=1）なので、置いた瞬間に隣と1.5cm以内なら失敗。
* **(L3) 同一レーン（同じx帯・同じz帯）は必ず奥→手前の順**。
* **(L4) 扉は左が cut_x 分狭い**。`左端 < -0.51` に置く荷物は
  x_min で入って**左へ横スライド**する。そのスイープ範囲にある同じ(y,z)帯の荷物が先にあるとNG。
  → **各スラブ・各高さ帯で「左端の荷物を最初に」置く**。
* **(L5) 小棚は左帯 x∈[-0.96,-0.52] の z∈[0.805,0.845] を全奥行きで塞ぐ**。
  この高さをまたぐ荷物は左帯に置けない（実測でNG確認）。
* **(L6) 【罠】底面 z が [棚上面, 棚上面+0.05] = [0.845, 0.895] に入る荷物**は
  コードが「棚直置き」と誤認して持ち上げ量が0になり、**真下の支持荷物と衝突して即死**。
  実測: 支持天面0.840・目標底面0.850 → `is_valid=False` でエピソード終了。
  → **プランナはこの高さ帯を回避するか、1.6cm以上浮かせて落とす**。
* **(L7) 同様に上面が 0.7715〜0.805 / 1.5365〜1.57 に来る積み荷も持ち上げ量が消えて即死**。
* **(L8) 壁・蓋・床とは経路衝突判定をしない**。障害物は「他荷物・大棚・小棚」のみ。

### 2.3 整定と誤差

* 配置は目標位置へワープ→300ステップ整定。実測ドリフトは 1〜1.6cm（積層で累積）。
* **設計値ではなく毎ステップ観測される `packed_items[].pos/orn` を使って再計画すること**。
  実測で「1.7cmの設計隙間がドリフトで1.3cmになり搬入失敗」を確認済み。

### 2.4 評価（`evaluator.py`）

* `fill_score = 100 × Σ(完全内包の荷物体積) / Σ(コンテナ有効容積)`。
  **整定後の実姿勢の8隅**すべてが margin 判定を通る必要がある。
  ローカル設定(-0.005)では**床直置きの荷物は底面が床平面と一致するため除外される**
  （実測: 36個積んで22個しか計上されず 28.99%）。
  README には「評価時は検証時より緩い」とあるので本番は正の margin と推測されるが、
  **側壁・奥壁・天井からは最低5mm、できれば1.5cm以上離す**設計にして両にらみする。
* 課題000: 全荷物体積 2.60 m³ / 容積 4.007 m³ → **fill_score の理論上限は約 65 点**。
  つまり fill を伸ばす唯一の道は「全部積む」。
* `Container.create_cap()` はローカルでは未使用 → **本番の動的安定性テストで蓋をするためのフック**。
  ローカル評価に自前で実装して安定性スコアの代理指標を作れる。

### 2.5 実行時間（実測）

| 状況 | env.step 所要 |
| --- | --- |
| 積載0個 | 0.012 s |
| 積載12個 | 0.17 s |
| 積載30個 | 0.46 s |

→ おおよそ `0.012 + 0.015 × 積載数` 秒。
**policy の8秒制限内で、40個積載時でも本物の物理検証を10回以上回せる**。
optimize の180秒なら全40手のフルロールアウトが十数回。**物理をループに入れた探索が可能**。

## 3. スコア構造とレバレッジ

| 項目 | 上限に効く要因 | 打ち手 |
| --- | --- | --- |
| fill_score | 全荷物を積めるか（上限65点前後） | 密度＋無失敗 |
| num_placed_items | 同上。これが閾値未満だと**他スコアが全部0** | 最優先 |
| cog_score | 重心の低さ | 重い荷物（18/13/12kg）を下層へ |
| placement / soft | 優先手荷物・ソフト貨物の上に一般荷物を置かない／優先コンテナ指定 | 種別ごとに**列を分離**、softは各列の最上部へ |
| stability | 蓋をして重力変動 → ずれ量 | 低重心・列構造・天井まで詰める |

**方針**: 「無失敗で全積み」が支配的。その制約下で cog と種別分離を同時に満たす配置を選ぶ。

## 4. 解法アーキテクチャ（3層）

```
┌─ Layer 3: プランナ ────────────────────────────────┐
│  offline: ビームサーチ + LNS(ruin&recreate) + パターンDB  │
│  online : スラブ構築 + 多目的スコアの貪欲/ビーム            │
├─ Layer 2: 候補生成 ────────────────────────────────┤
│  Extreme Points（コンテナ構造面 + 既存荷物の角）× 6姿勢     │
│  奥詰め・左右壁寄せ・1.5cm隙間へスナップ                    │
├─ Layer 1: 実行可能性オラクル（numpyのみ, µs オーダー）──────┤
│  inclusion() / transport_path() / support() を validator と │
│  ビット単位で一致させる（罠 L4〜L7 を含む）                 │
│  + 任意で PyBullet デジタルツインによる物理検証             │
└────────────────────────────────────────────────┘
```

### Layer 1 が最重要
`src/ground_handling/validator.py` の論理を numpy で厳密に再実装する。
軸平行ボックス同士なので、スイープ経路は**軸平行ボックスの掃引 = 1個のAABB**として厳密に書ける。
距離判定は PyBullet と同じ「ユークリッド距離 ≤ 0.015」で実装する
（軸ごとギャップ `sqrt(Σ max(0,gap_i)²) ≤ 0.015`）。

**検収条件**: ランダム配置10万件で実シミュレータと判定が100%一致すること（ファジング）。

### Layer 3 の中核構造 —「スラブ（壁）構築」

奥行き Y を奥から手前へスラブに分割し、各スラブを (X,Z) 断面の2D詰め込み問題として解く。

* 搬入可能性が構造的に保証される（前のスラブは空だから経路が通る）。
* 隙間コストは **Yのスラブ境界ごとに1.5cm**、**Xの隣接ごとに1.5cm**、**Zは0**。
  3列×5スラブなら損失は約 0.24 m³ ≒ 容積の6%。
* 列構造なので安定性・重心制御と相性が良い。

**縦積みがタダ**という性質から、**X方向の列数とY方向のスラブ数を減らし、Z方向に積む**のが基本形。

## 5. 手法調査と本問題への適合

| 手法 | 出典/概要 | 本問題での位置づけ |
| --- | --- | --- |
| Extreme Point ヒューリスティクス | Crainic, Perboli, Tadei (INFORMS J. Comp.) | **候補生成の標準**。追加制約を入れやすく本問題に適合。採用 |
| ビームサーチ / CBD-BS | Benders分解＋EPベースのビームサーチ | **オフライン最適化の主力**。180秒に収まる。採用 |
| ruin & recreate / LNS | 大規模近傍探索 | ビーム解の磨き上げ。採用 |
| MCTS + lookahead | 先読みパーセルを使うオンラインBPP | 課題B（プールk個）で有効。物理オラクルが安いので現実的。採用候補 |
| DRL（PCT, ICLR'22 / O4M-SP 等） | 学習方策で online 3D-BPP | 学習基盤の構築コストが高く、**即死ペナルティのある本問題ではリスクが高い**。第2段階の候補 |
| パターンDB（列生成的） | 固定カタログ前提の断面パターン事前計算 | 荷物が7種固定という本問題特有の強み。**提出物に同梱可能**。採用 |

**推奨**: まず「厳密オラクル + EP + ビーム/LNS」で上位を確保し、
余力があればスコア関数の重み学習（ベイズ最適化）や価値関数の学習を足す。
RLをゼロから回すより、**物理シミュレータをループに入れた探索**のほうが本問題では費用対効果が高い。

## 6. 課題パターン別の戦略

### 課題A（オフライン有り, lookahead=1, 40〜80個）
* `optimize` の180秒で **順序と配置を同時に決める完全プラン**を作る。
  内部に `self.plan = [(item_index, container, pos, orn), ...]` を保持し、返り値は順序だけ。
* `policy` はプランを再生するだけ。ただし**毎ステップ観測姿勢でオラクル再検証**し、
  ずれていれば同一荷物の代替位置へ**その場で修復**（順序は変えられないため位置で吸収）。
* 180秒の使い方: ビームサーチ(〜60s) → LNS(〜60s) → 物理ツインで全手ロールアウト検証(〜40s)。
  タイムアウトは致命的なので **150秒でハード打ち切り**。

### 課題B（オフライン無し, lookahead 3〜40）
* 初回 `policy` 呼び出し（8秒）で見えている k 個から**プラン骨格**を構築。
* 以降は毎ステップ 8秒のうち ~1秒で「次の1手」を決め、残りで先の計画を改善（計画の分割償却）。
* プールから**「今の最良スロットに最も合う荷物」**を選ぶ。k が大きいほど課題Aより有利。

### 課題C（オフライン無し, lookahead=1）
* 事前計算した**スロット・テンプレート**（7種カタログ向けに設計した断面パターン）を持ち、
  到着した荷物を最適な空きスロットへ割り当てる。
* **予約ルール**: 常に最大サイズ（0.75×0.56×0.27）が入る空間を1つ以上残す。
  残せなくなったら以降は小型優先で詰める。
* 最後はEP貪欲＋オラクルにフォールバック。

### 共通
* 2コンテナ時は `place_pos` が `(offset_x,0,0)` 基準の**相対座標**、
  `packed_items[].pos` と `points/n_vecs` は**世界座標**。ここの取り違えは頻出バグ。
* 優先コンテナがあれば優先手荷物はそちらへ。無ければ扉側・上層に配置（取り出しやすさ＝減点回避）。
* soft は「上に一般荷物を置かない」＝**各列の最上段 or soft専用列**にまとめる。

## 8. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| policy タイムアウト | ランダム行動→**即死** | 内部デッドライン6.5秒。最初に「安全な1手」を確定させてから探索で改善 |
| optimize タイムアウト | 計画が無効化 | 150秒で打ち切り。途中結果を常に保持 |
| 罠 L6/L7 の高さ帯 | 即死 | オラクルで厳密に禁止 |
| 整定ドリフト | 設計隙間が消えて搬入失敗 | 観測姿勢ベースで毎手再検証。隙間は 1.5cm ではなく **2.0〜2.5cm** を既定に |
| 過学習（サンプル config 依存） | 本番で崩壊 | 寸法は必ず `container_list` から導出。ハードコード禁止。シーン生成器でランダム化テスト |
| メモリ12GB / ネット不可 | 実行失敗 | PyBullet ツインは1インスタンス使い回し。外部通信なし |

## 9. 実装状況（2026-08-29）

`agents/submit/` に v1 エージェントを実装済み（`agents/submit.zip` が提出物）。

| ファイル | 役割 |
| --- | --- |
| `geometry.py` | Layer 1: `validator.py` を numpy 不要の純Python数式で厳密再現するオラクル。内包判定・搬入経路のスイープ判定・棚/小棚のジオメトリ導出・罠L6/L7回避 (`safe_stack_bottom_z`) を実装 |
| `packer.py` | Layer 2/3: 行(Row)ベースの床詰め候補生成、単一支持台への完全ネスト＋隣接2台にまたがるペア支持（`_footprint_supported` で未支持オーバーハングが出ないことを保証）、奥から手前への充填を支配的にするスコアリング、密グリッドへのフォールバック探索 |
| `agent.py` | `optimize`/`policy` の実装。`optimize` は体積・footprint・高さ・質量の4種のソートキーを仮想シミュレーションで比較し最良の順序を採用。`policy` は `observation` から毎回状態を再構築する自己完結設計（タイムアウト再起動後も `get_init_states` なしで動作）。例外は握りつぶして必ずフォールバックを返す（1手の失敗よりタスク全体のクラッシュの方がはるかに悪いため） |

### 動作確認

- `scripts/run_test.py` を実サンプルconfig（本番同等のタイムアウト: init 10s / optimization 180s / policy 8-10s）でエンドツーエンド実行し、**タスク000・001とも `status: success`、クラッシュ・タイムアウトなし**を確認（所要時間はタスク000で optimization 2.3秒 / policy 最大0.08秒、いずれも予算に対して大きな余裕あり）。
- 途中まで（タスク000で約22手、タスク001で約16手）は無失敗で配置できるが、その後は自作の総当たりフォールバックでも有効な配置が見つからず、エピソードが早期終了して部分点で確定する（`status: success` のまま。README記載の「失敗したらそのシーンの積付は終了しその状態で評価」通りの安全側の挙動で、タスク全体がクラッシュすることはない）。
- 詰まった時点でのコンテナ体積使用率は約35〜40%（`fill_score` 自体は §2.4 の理由でこれより低く出る）。原因は貪欲ヒューリスティクスが床上の配置をグローバルに調整せず、行/列の整列が崩れて断片化すること。単一支持台への完全ネスト、隣接2台へのペア支持、行クラスタリングなど複数のヒューリスティックを追加したが、この「早期の断片化」自体は解消しきれていない。

### 既知の制約と次の一手（v2以降）

1. **真のシェルフ/スカイライン床詰め**: 現状は箱の辺から候補点を生成する準最適な方式。行を明示的なオブジェクトとして永続管理し、各行の中で1次元ビンパッキングを厳密に解く実装に置き換えると、断片化が大きく減る見込み。
2. **N個の隣接支持台へのブリッジ**: 現在は2台までのペア支持のみ対応。3台以上の隣接支持台をクラスタ化して統一床とみなす拡張で、スタッキング機会がさらに増える。
3. **`optimize`のビームサーチ化**: 現在は4種の静的ソートキーを仮想シミュレーションで比較するのみ。180秒の予算のうち数秒しか使えていない（実測2.3秒）ので、ここにビームサーチ/LNSを載せる余地が大きい。
4. **fill_scoreの床フラッシュ問題**: `FLOOR_LIFT` は配置検証（warp直後）には効くが、300ステップの物理整定で重力によりほぼ相殺され、最終的に床と面一になる。評価基盤側のマージンが緩い前提で許容しているが、要確認。

現状のv1は「1手も失敗しない」という戦略の核となる部分（オラクルによる無効手の排除、例外の完全握りつぶし、タイムアウト再起動への耐性）を満たしており、詰まった場合も部分点で安全に着地する。上記の改善で床/スタック利用率を伸ばすのが次のステップ。

## 10. 低スコアの原因分析と v2（2026-08-29）

LBスコアが低い原因を実測で分解した結果、**独立した2系統の問題**が判明した。

### 10.1 問題A: 積み残し（支配的）

v1は課題000で41個中18個(44%)、課題001で42個中16個(38%)しか積めずに早期終了していた。
README の「手荷物を一定数以上積載できていないと**充填率スコア以外は0**」という条項に照らすと、
この積載率では cog / stability / placement / soft の4項目が全て0になっている可能性が高く、
LBスコアが極端に低い最大の理由と考えられる。

原因は4つあり、いずれも実測で切り分けて修正した。

| # | 原因 | 実測 | 対処 |
| --- | --- | --- | --- |
| A-1 | **探索範囲の定義バグ**。`x_lo` が左ノッチ帯を丸ごと除外し、`y_lo` が扉側（壁が無い）にも `thickness` を引いていた | コンテナ体積の **29%** を最初から探索対象外にしていた | 実際の内包平面に合わせて修正。ノッチ帯は搬入経路オラクルが可否を判定する |
| A-2 | **探索の打ち切りバグ**。候補を900件で打ち切っていた | 有効な候補が48件あるのに最初の有効候補がランク2376で、探索は「配置不能」と誤判定していた | 打ち切りを暴走ガード（60000）に緩和。実予算は呼び出し側のデッドラインで管理 |
| A-3 | **候補生成が疎すぎる**。極点（既存箱の辺）のみを候補にしていた | 密グリッドでは **848件**の有効配置があるのに極点探索は **0件** | 極点で見つからない場合の密グリッド探索を段階的に追加 |
| A-4 | **支持面の断片化**。「同一高さの箱の集合」を支持レベルとして列挙していた | 19個の箱に対し支持レベルが **20個**（＝全部バラバラ）で、載せられる平面が存在しなくなる | レベル列挙を廃止し、**落下着地点モデル**（`_landing`）に変更。(x,y,姿勢)だけを列挙し、高さは着地位置から導出 |

さらにスコア重みを実測スイープで調整した。純粋な層構築（高さ優先）も純粋な壁構築（奥行き優先）も
どちらも劣り、両者を同程度に重み付けした `W_LOW=400 / W_BACK=200 / W_FLAT=100` が最良だった。

### 10.2 問題B: 床置き荷物が充填率に計上されない

`evaluator.calculate_fill_rate` は荷物の8隅すべてが全平面から `inclusion_margin`(=-0.005) 以上
内側にあることを要求する。床に接した荷物は底面隅が床平面と一致する（実測 dot ≈ +1e-5 > -0.005）ため
**除外される**。実測では配置済み体積の **28〜32%** がこの理由だけで充填率に計上されていなかった
（除外理由の内訳を集計したところ、ほぼ全てが `floor` 平面）。

README には「内包判定は検証時よりも緩く設定されている」とあり、本番評価基盤では正のマージンで
床置きも計上される可能性がある（配布コードは validator と同じ -0.005 を渡しており README と矛盾する）。
どちらでも損をしないよう、側壁・奥壁・天井からは十分離す設計を維持する。物理的に床から5mm浮かせる
ことはできないため、この問題自体は解消できない。緩和策は「床接地層の体積を最小化し、層数を稼ぐ」こと。

### 10.3 v2 の結果

| | 課題000 fill | 課題000 積載 | 課題001 fill | 課題001 積載 |
| --- | --- | --- | --- | --- |
| v1 | 14.92 | 44% | 8.79 | 38% |
| **v2** | **30.16** | **56%** | **17.27** | **40%** |

両課題とも `status: success`、クラッシュ・タイムアウトなし。
処理時間は optimization 17.7秒/180秒、policy 最大 5.06秒/8秒。

### 10.4 残る課題（v3以降）

1. **まだ積み残している**（56% / 40%）。停止時点で密グリッド探索でも有効配置が0件であることは確認済みで、
   探索の取りこぼしではなく**レイアウトそのものが詰まっている**。真の改善には貪欲法をやめ、
   §7 の計画（ビームサーチ＋LNS）で先読みしながら配置を決める必要がある。
2. **重みは2シーンのみでの調整**であり過学習の懸念が大きい。シーン生成器を作って
   ランダムシーン群で評価する仕組みが先に要る。
3. **`optimize` の180秒予算がほぼ未使用**（17.7秒）。ここにビームサーチを載せるのが最もコスパが良い。
4. 探索が本当に配置不能と判断した場合、未検証の座標を返している（どのみちエピソードは終了するので
   スコアには影響しないが、ログ上 `is_valid: False` となり原因分析を紛らわしくする）。

## 11. 7シーン評価ハーネスと専門家レビュー、level-match の試行と撤回（2026-08-30）

### 11.1 7シーン評価ハーネス

サンプルconfigは1コンテナ・オフラインなし・棚なし・初期荷物なしの2パターンしか無く、
本番で出題される「2コンテナ」「棚あり」「初期荷物あり」「優先コンテナあり」の組み合わせを
一度もテストしていなかった。`scenegen.py`（7種の荷物カタログから乱数生成）と `harness.py`
（fill・積載率に加え、断片化指標＝「配置済み箱の個数」に対する「異なる支持面高さの個数」の比を
出力）をスクラッチパッドに作成した。理論上限（全荷物が入った場合のfill_score）との比較で、
**貪欲法は理論上限の23%しか達成できていない**ことを実測した。

| シーン | 構成 | 理論上限 | 実測 |
| --- | --- | --- | --- |
| A | 1コンテナ・オフラインあり | 63.3 | 22.9 |
| B | 棚あり・pool10 | 65.6 | 8.8→13.6(bigfirst後) |
| C | 初期荷物あり | 68.3 | 11.0 |
| D | 2コンテナ・オフライン | 64.7 | 24.7 |
| E | 2コンテナ・優先コンテナ | 55.1 | 14.7→18.2(bigfirst後) |
| F | 2コンテナ・棚・初期荷物 | 55.0 | 6.7 |
| G | pool40 | 72.4 | 14.4→24.4(bigfirst後) |

### 11.2 専門家レビューで得た知見と、検証で誤りと判明した点

最適化問題の専門家（サブエージェント）にレビューを依頼した。中心的な主張
「これは密度の問題ではなく到達可能性(reachability)の問題であり、探索を強化しても意味がない。
構造化されたレイアウト表現（レベル→行→フロンティア）への転換が必要」は、
「2cm密グリッドでも有効配置0件、しかし容積の75%が空」という実測と整合し、採用した。

一方、提案の一部はソースコードで裏取りした結果**誤り**と判明した。

| 専門家の主張 | 検証結果 |
| --- | --- |
| 「マージンを詰めれば0.65m幅の荷物が3列入る」 | 誤り。外寸2.0mで計算していたが**内寸は1.92m**で、0.65×3=1.95は元々入らない。実測でも列数は変化せず |
| 「行内は外側X→扉XのX順に埋めるべき」 | 誤り。ソース確認の結果、荷物は**自分自身の目標X**から進入する（`rel_x = clip(target_x, x_min, x_max)`）。X方向の共有廊下は存在せず、順序制約は左ノッチ帯のみ |
| 「配置不能な荷物をスキップできるか要確認」 | できない。`env.step` の全失敗経路が `terminated = True` |

外部レビューは有用だが、**検証可能な主張は必ず自分で裏を取る**必要がある。

### 11.3 bigfirst（largest-first）の確定

プールに選択の余地がある時、単純な位置スコアだけでは小さい荷物から消費されて大物が
行き場を失う。荷物体積に比例したボーナス `W_ITEM_VOL=3000` を追加し、7シーン合計で
**103.2 → 122.2** を確認、デフォルト値として確定済み（`packer.py`）。

### 11.4 level-match ボーナスの試行と撤回

19個の箱に対し支持面レベルが20個という断片化（`_landing`が毎回バラバラな高さで着地）を
是正するため、「コンテナ内で既に複数の箱が共有している天面高さに一致する配置」に
ボーナスを与える `W_LEVEL_MATCH` を実装した。結果は**撤回**した。理由は2つ。

1. **fill_scoreが悪化**（7シーン合計 122.2 → 116.9、重み350の場合）。断片化指標(lvl/box)自体は
   改善したが、副作用として床面の新規開拓が増え（同一カラムを伸ばすのではなく別のカラムへ
   拡散する挙動が実測で確認された）、総合スコアは下がった。
2. **より重大な問題として、実行時間が数倍に悪化した**。7シーンハーネスが通常1〜2分で終わるところ、
   弱い重み(100)でも5分以上かかった。単発の `best_placement` 呼び出しでは有効候補到達までの
   検証回数がW=0で15回、W=100/350で31回とほぼ変化しておらず、単純な検証スキップでは
   説明がつかない。lookahead=40のシーンでは `choose_action` が1ステップで最大40回
   `best_placement` を呼ぶため、この根本原因は未特定のまま、**本番の8秒制限に対する
   タイムアウトリスクだけが確定的に上がる**という状況だった。品質が横ばい以下でリスクだけ
   増える変更は正当化できないため、`W_LEVEL_MATCH=0.0` に戻して撤回した（コードは無効化した
   まま `packer.py` に残置、再挑戦する場合の起点として）。

「既存の支持面を再利用する」という発想自体は正しいと考えられるが、**グローバルに
（コンテナ全体でどこでも良いから一致する高さを探す）** ではなく、**ローカルに
（今まさに伸ばそうとしているカラム自体の高さと一致するか）** スコープすべきという仮説を
残した。次に着手する場合はここから。

### 11.5 次の一手

上記の通り、軽量な「スコアリングのひと押し」では断片化は解消しなかった。専門家案の
本命である**レベル/行を明示的なデータ構造として持つパッカーへの書き換え**（§7）が
引き続き最有力の次の一歩。ただし本セッションでは着手していない（規模が大きく、
7シーンハーネスでのA/B比較なしに投入するのはリスクが高いため）。

## 12. 実験手法そのものの監査と、多スタート化の試行（2026-08-30）

前節までの結論を鵜呑みにせず、「この分析プロセス自体は信頼できるのか」を監査した。
文献調査（web検索）と、方法論に特化した第三者レビュー（別セッションの専門家）の
両方を行い、**測定基盤そのものに再現性のバグがあった**ことを発見・修正した。

### 12.1 文献調査で分かったこと

- 自作のスコア式（奥優先→低優先→左優先）は、**Deepest-Bottom-Left-Fill (DBLF)** という
  確立されたヒューリスティクスそのものだった。独自に発見していたことになる。
- 一方、断片化を防ぐ本命は **George & Robinson (1980) の "wall-building"** 系列の手法。
  容器の奥行き方向（Y軸、荷物が扉から侵入してくる方向）に沿って **壁（Y方向の帯）を
  奥から手前へ**構築し、各壁の中では**層（Z方向）を下から上へ**埋めていく。
  Bischoff & Marriot (1990), Gehring et al. (1990), Pisinger (2002) など多数の後続研究の
  基礎になっている、40年以上検証されてきた構造。本問題の物理（縦積みは無料、Y方向は
  奥から手前の順序制約が必須）と完全に整合する。
- パラメータ調整の定石として `irace`（Iterated Racing、F-Raceベース）を確認したが、
  後述の理由で**今回は適用対象ではない**と判断した。

### 12.2 方法論レビューで発覚した問題：測定の非決定性

7シーンハーネスを2回連続実行すると完全一致するが、**CPU負荷が異なる状況（並列実行）で
再実行すると結果がずれる**ことを発見した（実測: シーンE_2c_priority で fill 18.2 vs 18.8）。

原因はコード上で確認済み: `choose_action` が「残り時間 ÷ 候補数」で各候補の検証に
壁時計の締切を割り当てており（`packer.py`）、システム負荷次第で締切が発火するタイミングが
変わり、結果が変わる。本番の8秒制限を守るためには必要な機構だが、**この機構を研究用の
比較にもそのまま使っていたため、比較結果の一部がノイズだった可能性がある**。

**修正**: 研究用ハーネス（`harness2.py`）に `research` モードを追加。壁時計の締切を
3600秒（実質無制限）にし、代わりに既存の決定論的カウンタ `MAX_VALIDATIONS`
（検証した候補数の上限）だけを効かせる。これにより：

- 同一設定を並列実行しても**work_units・fill・norm%が完全一致**することを確認（wall_sだけ自然にばらつく）。
- 本番相当の `production` モード（実際の `agent.policy()` をそのまま呼ぶ）は別途残し、
  **品質比較には使わず、タイミングのpass/fail検証専用**とした。

この2つを分離した結果、追加の発見があった: 7シーン中3シーン（B, E, G）で実際に
締切が発火していたが、影響は限定的だった。

| モード | mean norm% | min |
| --- | --- | --- |
| research（無制限） | 27.8% | 12.2% |
| production（本番8秒） | 27.3% | 12.2% |

締切発火の影響はシーンGで最大（fill 25.1→27.1、約7%相対）、Eで中程度（約3%）、Bはゼロ。
**無制限予算でも平均27.8%にしかならない**ことから、時間切れは副次的要因であり、
主要因ではないと定量的に確認できた（§10.4の「レイアウトそのものが詰まっている」という
以前の定性的な結論を、数値で裏付けた形）。

### 12.3 スコアの集計方法も見直した

以前は7シーンの `fill_score` を単純合計していたが、これは**理論上限(ceiling)が高いシーンが
合計を支配する**という欠陥があった（レビュー指摘）。`fill/ceiling` に正規化した
`norm%` を導入し、平均と最小値の両方を報告する方式に変更した。

### 12.4 devプール（16シーン）を追加

既存の7シーン(A〜G)は既に bigfirst の採否判断に使われており、今後のチューニングに対して
「汚染された」（過学習を検出できない）データセットになっている。`scenegen_pool.py` で
新たに16種類のシーン（コンテナ数・棚・初期荷物・優先コンテナ・lookahead・オフライン最適化の
有無をランダムに組み合わせ）を生成し、`scenes_dev.json` として分離した。
**今後の変更はdevプールで判断し、A〜Gは最終確認にのみ使う**運用とする。

### 12.5 `irace` を採用しなかった理由

レビューで指摘された通り、irace（F-Race）は「大きな母集団からサンプルした問題群に対し、
統計的検定で劣った設定を早期に切り捨てる」ためのツール。今回の7シーンは**母集団からの
サンプルではなく手作りの固定シーン**であり、7回評価すれば母集団全部を見終えている。
ノイズもresearch modeへの変更で解消済みなので、「ノイズあり・大規模母集団」を前提とする
irace系の統計機構は今は不要。優先度が上がるのは、devプールが本物の分布に近づき、かつ
アルゴリズム自体に確率的要素（下記12.6）を入れた後。

### 12.6 `optimize` の多スタート化（GRASP的ランダム化）と、その結果

無制限予算でも大半のシーンで締切ヒットが0回だった（=予算に余裕がある）ことを踏まえ、
`agent.py` の `optimize()` を拡張した。従来は体積・footprint・高さ・質量の4種の
固定ソートキーを試すだけだったが、この4特徴量の**重みをランダムに変えた追加試行**を、
実測した1試行あたりのコストから残り予算に収まる回数だけ動的に追加するようにした
(`make_random_key` / GRASP風のmulti-start)。乱数シードは荷物リストから決定論的に
導出しており、新たなノイズ源にはならない。

**結果: A・D・devプールの45個シーンの3シーンで検証したが、いずれも旧コード（4種固定）と
完全に同じ結果になった**（試行回数は6〜7倍に増えたにもかかわらず）。この変更は
「悪化はしない」ことを保証する設計（既存解より厳密に良い場合のみ採用）なので安全に
残しているが、**効果は実証できていない**。

この負の結果自体に診断的価値がある。もし詰まりの原因が「荷物の投入順序が悪い」ことなら
多スタートが効くはずだが、効かなかった。つまりボトルネックは**`optimize` が制御する順序
ではなく、`policy`/`best_placement` が制御する配置ロジックの形そのもの**にある可能性が
高まった。§11.5・§7で挙げた「壁構築への書き換え」が、これで一段と根拠を増した形になる。

### 12.7 結論：効率的な進め方（第三者レビューの要約）

1. **測定基盤を先に固める**。ノイズのある評価軸の上でどれだけ丁寧に比較しても、
   結論の信頼性はノイズの大きさで頭打ちになる。今回は締切発火という具体的なノイズ源を
   特定し、決定論的な予算に置き換えることで解消した。
2. **7個の手作りシーンに統計検定を持ち込まない**。n=7は検定の検出力が無く、
   そもそも母集団からのサンプルでもない。「7個中何個改善したか」を正直に報告する方が
   誠実。判断に迷ったらシーンを増やす（devプール）。
3. **合計ではなく正規化して報告する**。理論上限で割ってから平均・最小を見る。
4. **「予算を使い切れているか」を先に測ってから、予算を増やす方向の改善（多スタート等）を
   試す**。今回は予算に余裕があることを確認した上で多スタートを試し、効果ゼロという
   明確な結果を得た。これにより「次はここに投資すべきではない」ことが分かった——
   これも十分に価値のある成果。
5. **一つの変更を「品質」と「コスト」の2軸で見る**。level-match（§11.4）のように
   品質が横ばいでコストだけ増える変更は、品質改善そのものより悪い。

## 13. wall-building構造の実装（2026-08-30）

§11.5・§12.1で本命としていた George & Robinson (1980) wall-building 構造を実装した。
Y方向の候補生成を「箱の辺ベースの自由な探索」から「壁（Y方向の帯）構造を考慮したもの」に
変更し、同じ壁の中で高さを揃えるスコアリングボーナスを追加した。試行錯誤の過程を含めて
記録する（今回も「測ってから確信する」を徹底したため、最初の2回は失敗している）。

### 13.1 実装の変遷と各段階での失敗

| 版 | 内容 | 結果 |
| --- | --- | --- |
| v1（純粋制限） | Y候補を壁の背面エッジのみに制限 | **fill 22.9→19.3に悪化**。壁の奥行きに満たない荷物は背面フラッシュにしか置けず、壁の手前側の空間が丸ごと死んだ |
| v1 + `_infer_walls`にstatic_obstacles混入 | (バグ) 小棚（幅は狭いがY方向は容器ほぼ全幅）が壁クラスタリングに巻き込まれ、コンテナ全体が1つの壁に吸収された | **fill 0（何も置けない）**。デバッグで即発見・修正（static obstaclesを壁推論から除外） |
| v2（ハイブリッド） | 従来の箱辺ベースのY候補 **に追加する形** で壁背面エッジも候補に含める。壁はスコアリングのヒントとしてのみ使う | 基準値(fill 22.9)に復帰。退行なし |

**教訓**: 候補生成を「制限」するのは危険。既存の自由な候補集合に**追加**する形にすれば、
理論上「悪化しない」ことを構造的に保証できる（既存候補が全て残るため）。

### 13.2 レベルマッチのスコープをローカル化

§11.4で撤回した level-match ボーナス（「コンテナ中どこでも良いから既存の天面高さに
一致する配置を優遇」）を、今回は**壁構造がある**ため正しくスコープできた：
「同じ壁の中で既に使われている高さに一致するか」だけを見る `_wall_local_tops`。

実装直後、単体テスト（2荷物を手動配置）ではボーナスが機能することを確認したが、
**フルエピソードでは全く効果が出なかった**（fill完全一致）。原因を調べたところ、
`TOP_TOL`（支持面クラスタリング用の1.2cm許容差）をこの用途にも流用しており、
カタログの「平置き高さ」（0.20〜0.27m、荷物種によって最大3cm差）を捉えられていなかった。
**用途の異なる2つの許容差を同じ定数で共有していたのが原因**。`WALL_HEIGHT_TOL`(3.5cm)
として分離し、`TOP_TOL`（支持面クラスタリング）とは独立に調整できるようにした。

分離した直後、今度は逆に**全体的に悪化**した（28.3%、A単体）。これは緩めた許容差を
誤って`_landing`側の`TOP_TOL`にも適用してしまっていた実装ミスによるもので、
定数を正しく分離した後は解消した。

### 13.3 最終結果

7シーンのうち、**offline optimize()があるシーン（A, D）は完全に無変化**（fillが1桁まで
完全一致）。これは§12.6の多スタート化の知見と整合する：`optimize()`は多数のランダム化
試行を行うため、ある1つのスコアリング項の効果が「別の試行順序で同じ場所に辿り着く」ことで
埋もれてしまう。

一方、**offline optimizeがないシーン（オンライン専用、B）では明確な改善**が出た：

| シーン | 構成 | 変更前 fill | 変更後 fill | 変化 |
| --- | --- | --- | --- | --- |
| A | 1コンテナ・オフラインあり | 22.9 | 22.9 | 変化なし |
| B | 棚あり・pool10・オンライン専用 | 13.6 | 16.4 | **+21%** |
| C | 初期荷物あり・lookahead=1 | 11.0 | 11.0 | 変化なし（元々選択の余地が少ない） |

work_units・wall_sはBで**悪化せず、むしろわずかに改善**（860731→855888、28.0s→27.3s）。
§11.4のlevel-matchで懸念されたタイムアウトリスクは再発していない（原因はグローバル探索の
組み合わせ爆発だったと考えられ、壁スコープのローカル探索ではそれが起きない）。

### 13.4 全7シーンでの最終判定：正味は悪化、レベルマッチは撤回

D, E, F, G を含む全7シーンで最終確認した結果、**正味は悪化**だった。

| シーン | 変更前 fill | 変更後 fill | 変化 |
| --- | --- | --- | --- |
| A | 22.9 | 22.9 | 変化なし |
| B | 13.6 | 16.4 | **+21%** |
| C | 11.0 | 11.0 | 変化なし |
| D | 24.7 | 22.4 | **-9%** |
| E | 18.6 | 13.2 | **-29%** |
| F | 6.7 | 6.7 | 変化なし |
| G | 27.1 | 27.1 | 変化なし |
| **mean norm%** | **27.8%** | **26.5%** | **-1.3pt** |

Bの改善（+21%）よりもDとE、特にEの悪化（-29%）が大きく、全体では悪化した。
§12.7で自分自身が定めたルール「スクリーニング用の一部シーンでの改善だけで採用しない、
全体集合で判断する」に照らし、**この結果を理由に `W_LEVEL_MATCH` を再び 0.0（無効化）に
戻した**。level-matchというアイデア自体は、グローバル版（§11.4）→ローカル（壁）版（今回）
と2回試して2回とも撤回したことになる。

一方、**壁候補の生成インフラ自体（`_infer_walls`, `_wall_y_candidates`）は安全に残した**。
これはスコアリングボーナスと独立しており、重み0の状態で全7シーンにおいて
既存候補への追加のみ（削除なし）であることを構造的に保証しているため、実測でも
wall-building導入前の基準値（mean 27.8%）と完全一致することを確認済み。
将来、壁ローカルなスコープでの改善案を試す際の土台として温存する。

### 13.5 このセッション全体の総括

構造化パッカー（wall-building）は文献的に最も筋の良い次の一手だと考えて着手したが、
**実装した2つのバリエーション（純粋制限・ハイブリッド+ローカルレベルマッチ）は
いずれも全シーン平均では基準値を上回れなかった**。得られた教訓：

1. **候補を「制限」する変更は必ず退行リスクを伴う**。追加する形にすれば少なくとも
   悪化はしない、という設計原則が今回も有効だった（v1の失敗とv2の回復で実証）。
2. **静的障害物（棚）を空間クラスタリングに混ぜると壊れる**。今回は「コンテナ全体が
   1つの壁になり何も置けなくなる」という分かりやすい形で即座に発覚したが、
   同種のバグはもっと巧妙な形でも起こりうる。
3. **1シーンでの改善は全体評価をしないと採否を判断できない**。B単体では明確な
   勝ちに見えたが、7シーン全体では負けだった。§12.7のルールが実際に機能した瞬間。
4. **貪欲法のスコアリング単体を触るアプローチ（level-match等）は、もう2回試して
   2回とも撤回している**。次に着手するなら、スコアリングの微調整ではなく、
   §7で当初提案していた**ビームサーチ／LNSによる真の探索**（局所的なスコアリング
   ヒントではなく、複数の配置系列を実際に試して比較する）に進むべき段階にきている。
