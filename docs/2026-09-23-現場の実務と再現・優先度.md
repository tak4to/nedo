# 現場の手荷物積付をどう再現し、何を優先するか（2026-09-23）

調査対象は「実際の空港で手荷物がどう運ばれ、どう積まれているか」。出典は §7。ここで決めた優先度は、競技の採点式ではなく**現場の要求**を基準にしたもので、採点式との一致・不一致も併記する。

## 0. 結論（優先度）

| 順位 | 現場の要求 | 競技での現れ方 | こちらの状態 |
| --- | --- | --- | --- |
| **P0** | **積み残しを出さない**（積めない荷物は人手に戻り、便が遅れる） | 1手でも不正で即終了＝残り全損。足切り（個数） | 設計の中心。実行可能性オラクル＋4段救済ラダー |
| **P1** | **1台に詰める**（コンテナ台数＝搭載スペースとコスト） | 充填率スコア・配置個数 | 主要な最適化対象 |
| **P2** | **荷崩れさせない**（破損・作業者のけが・扉開放時の落下） | 安定性スコア（揺動テスト） | 代理計測あり。密度の従属変数で独立レバーではないと実測 |
| **P3** | **優先手荷物を先に降ろせる**（別コンテナ／後積み＝先降ろし） | 配置スコア（下敷き減点・専用コンテナ違反） | 下敷き回避のみ実装。**「扉側・上段に寄せる」は未実装** |
| **P4** | **壊さない**（ソフト・取扱注意品にテンションをかけない） | ソフト貨物スコア | 下敷き回避を実装 |
| **P5** | **重心を低く・中央に**（ULD重心規定と機体のCG計算） | 重心スコア | 実装済み（`W_MASS_HIGH` ほか） |
| — | **採点されないが現場では必須**: タグと取っ手の向き、降ろし順、左右の重量バランス、ULDの重量上限、ネット掛け | 採点式に無い | 未対応（§5に整理） |

**残り期間の配分**: 競技側の伸びしろは出尽くしている（LB 60 への根拠ある経路なし）。**現場整合の整理（この文書）を 10-26 の技術提案書の中核に充てる**のが、順位と独立した最大の価値。実装を1つだけ足すなら P3 の「優先手荷物を扉側・上段へ」（§6）。

## 1. 現場では手荷物はこう運ばれている

### 流れと時間

- チェックインカウンター（国内線は出発20分前に締切）→ 手荷物仕分けベルト → **仕分けベルトに流れてきた順に**コンテナへ積み付け → 牽引車でランプへ → ハイリフトローダーで貨物室へ搭載
- 羽田では通常日で**1日1万個超、繁忙期は2万個超**を扱う
- 積付は「限られた時間・限られた空間で、形状・重量・素材が多様な手荷物を瞬時に見極める」作業で、**作業者の感覚と経験に依存**している（NEDO の課題設定そのもの）

### 積み方（人の手順）

- **コンテナ1台に約50〜60個**（JAL 羽田の実測値）
- **重い・大きい荷物は下**。重量は前後左右に均等に散らす
- **ベビーカー・車椅子など壊れやすいものは上**
- **「取扱注意」タグの荷物は隙間に入れ、テンションが掛からないようにする**
- **タグが見える向き・取っ手を掴める向きに揃える**（降ろす側の作業のため）
- **優先手荷物（ファースト／上級会員／乗継）は別コンテナ、バラ積み、または後から積む**。到着後はベビーカー等 → 優先タグ付き → 一般、の順に流す（＝後入れ先出し）
- 重量のある荷物は取っ手ではなく2点で持つ（作業者の負傷防止）

### 規則側の要求

- ULD は**重量を計測**し、機体の重心計算（ロードシート）に入る。ULD 自体の**重心は底面中心の10%以内**に収める
- 荷崩れ防止のため**ネット・ストラップで固縛**し、扉を確実に閉める
- 受託手荷物の平均重量は **15.9 kg**（EASA 2022）。23 kg／32 kg の上限手前に山ができる。サイズは3辺和 158 cm が標準的な上限

### ロボット化の現状

- 実運用中のロボット積付は **260〜300個/時** 程度。Schiphol は2006年から導入、Grenzebach はフランクフルトで8時間あたり24トンを処理
- **ULD の斜めカット部（wing side）への到達性**がグリッパ設計上の論点として挙がっている。競技のコンテナが五角形断面で、斜面沿いの候補生成が効くのと同じ構造
- 視覚系で荷物の形状と向きを判定し、ハード／ソフト／不定形が混在する流れをそのまま扱うことが要件

## 2. 競技ルールは現場の何を写したものか

| 競技の要素 | 現場の対応物 |
| --- | --- |
| 課題C（先読み1、順序固定） | **仕分けベルトに来た順に積む**という基本形 |
| 課題B（プール3〜40から選択） | 仕分け済みバッファがあり、作業者が選べる状況 |
| 課題A（事前に順序を最適化） | 早発手荷物保管（EBS）で事前に並べ替えられる状況 |
| 搬入経路の干渉判定（扉からL字・1.5cm余裕） | ロボットアームが扉から入れて押し込む動作。接触＝破損・停止 |
| 目標の8cm上から落として整定 | 実機のリリース高さと着地の再現 |
| 1手でも不正なら即終了 | 積めない＝人手に戻る／便の遅延。**現場では最悪の事象** |
| 充填率スコア | コンテナ台数。詰められないと台数が増える |
| 重心スコア | ULD重心規定・機体CG |
| 安定性スコア（揺らし） | 輸送中・扉開放時の荷崩れ |
| 配置スコア（優先手荷物の下敷き・専用コンテナ） | 優先手荷物は先に降ろす必要がある |
| ソフト貨物スコア | 「取扱注意はテンションを掛けない」 |
| 個数の足切り（一定数未満なら充填率以外0） | 積み残しがあるならその積付は成立していない、という現場判断 |

**対応していない現場要素**: タグ・取っ手の向き、降ろす順序そのもの、左右の重量バランス、ULDの重量上限、ネット掛け、特殊品（ベビーカー・車椅子・スポーツ用品）の扱い、バラ積みへの切り替え。

現場・ロボットの制約は競技側の判定としてすでに定義されており、こちらは**評価器と同じ判定を配置前に厳密再実装**している（内包・L字搬入・支持・整定）。ここは再現済みで、変更しない。

| 現場の作法 | 実装 | 状態 |
| --- | --- | --- |

| 斜めカット部の活用 | 斜面沿いの候補生成（A-5） | 実装済み |

## 3.5 現場密度で測った結果（2026-09-23）

1台あたり50〜60個を供給する2集合（dev 32本 / ホールドアウト 32本）を作り、現行の提出版（`agents/submit`、オフライン150秒）で測った。`tools/poolgen_dense.py`、`tools/run_dense.sh`、`tools/dense_report.py`。

| 集合 | 供給 | 積載 | 積み残し | 終了原因 |
| --- | --- | --- | --- | --- |
| dense（dev） | 54.2 個/台 | **29.8 個/台** | 33.0 個/シーン | 詰まり30 / 崩落2 |
| densetest（ホールドアウト） | 54.5 個/台 | **28.8 個/台** | 36.0 個/シーン | 詰まり30 / 崩落2 |

参考: 40〜50個/台の既存4集合では 28.0〜31.1 個/台。

**分かったこと**

1. **積載数は供給量に依存しない。** 40〜50個/台でも50〜60個/台でも、積めるのは **1台あたり約29個で頭打ち**。律速は荷物の供給ではなく**詰め方**であることが、供給を1.35倍にしても積載が動かないことで確定した
2. **現場換算で1.85〜1.91台**。現場が1台に収める分量に、こちらは約2台使う
3. **崩落はほとんど起きない**（32本中2本）。終了原因の94%は「置き場所が見つからない」。**荷崩れ対策（P2）より詰まり対策（P0/P1）が支配的**という優先度が、現場密度でも変わらないことを確認した
4. 棚ありが最も弱い（27.5〜28.2 個/台 対 棚なし 29.2〜31.3）。既知の最弱セグメントが現場密度でも再現した

**注意（過大解釈を避ける）**: 公式カタログの荷物は平均66 L で、50個なら 3.29 m³＝コンテナ外寸の70%に当たる。壁・斜めカット・棚を差し引いた有効容積を考えると、**この寸法の荷物を50個積むことは幾何的にほぼ不可能**。現場の50〜60個は、より小さく変形もする実物の手荷物での数字である。したがって dense 集合は「現場と同じ個数を積めるか」を測るものではなく、**供給がコンテナ容量を明確に上回る状況（＝現場の常態）での詰まり方**を測るものとして使う。

## 4. 実務に即した優先度の根拠

現場の損失は次の順で大きい。

1. **積み残し（P0）**: 積めなければ人手に戻り、出発が遅れる。競技でも1手の失敗で残り全損なので、**現場と競技で一致している唯一の最重要項目**
2. **台数（P1）**: 詰められないとコンテナが増え、搭載スペース・便あたりコストに直結
3. **荷崩れ（P2）**: 破損補償と作業者のけが。扉を開けた瞬間に落ちてくるのが最悪
4. **優先手荷物（P3）**: 到着後の引き渡し順の約束。下敷きにすると約束が崩れる
5. **破損防止（P4）**: ソフト・取扱注意品
6. **重心（P5）**: 規定内に収まれば良い性質（閾値型）で、下げ続ける価値は小さい

競技の採点はこれを「個数の足切り → 5指標の加重平均」という形で近似している。**足切りが個数で決まるのは、現場の P0・P1 をそのまま写したもの**と読める。

## 5. 採点されないが現場で必要なこと（技術提案書の材料）

| 現場の要求 | なぜ採点に無いか | 実装するなら |
| --- | --- | --- |
| タグが見える向き・取っ手を掴める向き | 荷姿の向きは採点対象外 | 向きの候補を絞る制約として追加できる（自由度が減るので充填率と競合） |
| 降ろす順序（後入れ先出し） | 積付のみを採点 | 優先手荷物を扉側・上段へ誘導する項 |
| 左右の重量バランス | 重心スコアは高さ方向のみ | 左右のモーメント差をスコア項に |
| ULDの重量上限 | 荷物の総重量が上限に届かない設定 | 上限チェックを候補生成に |
| ネット掛け・扉際の処理 | シミュレーション外 | 扉付近の高さを制限する項 |
| 特殊品・バラ積みへの切替 | 競技の荷物カタログ外 | 対象外 |

この表は「アルゴリズムとして何を解いたか」ではなく「**現場に出すには何が足りないか**」を示すもので、技術提案書の最後の章にそのまま使える。

## 6.1 P3 の実装と測定結果（2026-09-23）— 「上段へ」は効く、「扉側へ」は逆効果、ただし採用しない

`agents/dev/packer.py` に `W_PRIO_DOOR` / `W_PRIO_HIGH`（ともに既定0）を追加。優先手荷物にだけ、奥選好（`W_BACK`）と低所選好（`W_LOW`）を打ち消す向きの項を掛ける。候補評価・棚下候補・計画再生の3経路すべてに同じ関数で適用（過去に2経路が乖離するバグがあったため）。優先手荷物を含む123シーン（既存4集合＋現場密度2集合から抽出、開発64 / ホールドアウト59）で測定。

| 条件 | 下敷き | 扉からの位置 | 高さ | 配置スコア | 積載率 vs 現行 (se) | fill (se) |
| --- | --- | --- | --- | --- | --- | --- |
| 現行 | 107 | 0.380 | 0.680 | 92.08 | — | — |
| 上段 100 | 99 | 0.398 | 0.694 | 92.96 | −1.17 (0.62) | −0.57 (0.34) |
| 上段 200 | 87 | 0.414 | 0.703 | 92.48 | −0.94 (0.52) | −0.58 (0.29) |
| 上段 300 | 87 | 0.431 | 0.717 | 92.48 | −1.52 (0.74) | −0.85 (0.42) |
| 上段 415.8 | **79（−26%）** | 0.439 | 0.758 | **93.66** | −1.41 (0.74) | −0.88 (0.41) |
| 扉側 326.87 | **141（+32%）** | **0.282** | 0.645 | 88.53 | −0.55 (0.55) | −0.45 (0.30) |
| 両方 | 125 | 0.313 | 0.743 | 90.22 | −2.64 (0.81) | −1.58 (0.44) |

（扉からの位置は 0=扉、1=奥。高さは 1=積み上げた山の天面）

**分かったこと**

1. **「上段へ」は現場の目的に効く**: 下敷きが最大26%減り、配置スコアも上がる
2. **「扉側へ」は逆効果**: 扉には寄る（0.380→0.282）が、**下敷きが32%増える**。扉側は後続の荷物が通り続ける場所なので、低い位置に置くと上から覆われる。**現場が優先手荷物の取り出しやすさを確保しているのは「扉側に置くから」ではなく「最後に積むから」**（＝結果として上に載る）。こちらの `W_PRIO_DEFER`（プール選択で優先手荷物を後回し）が既にその実装に当たる
3. **代償なしの重みは無い**: どの水準でも積載率が1〜1.5ポイント（約2 se）下がる

**判定: 既定OFFのまま残す。** §0 の優先度で P1（台数＝詰める）は P3（取り出しやすさ）より上であり、積載を1.4ポイント落として下敷きを26%減らす取引は、現場の優先度に照らして成立しない。採点上も、配置スコア +1.6 に対し個数・充填率が下がるので割に合わない。**「現場の作法をそのまま配置規則に翻訳すると裏目に出ることがある」**（扉側の件）は、技術提案書に書く価値のある知見。

## 6.2 ローカルの頭打ちの診断と、その対策の検証（2026-09-24）

### 診断: 詰まった瞬間に何が残っているか

現場密度・1コンテナ・詰まり終了の6シーン（`tools/void_budget.py`、コンテナ容積比の平均）。

| 内訳 | 割合 |
| --- | --- |
| 荷物が占める体積 | 52.1% |
| **スリバー（最小の荷物より狭い隙間）** | **23.6%** |
| 棚の下 | 7.8% |
| 十分広いのに使えていない空気 | 6.8% |
| 残り高さ不足の空気 | 5.3% |
| 覆われた空間 | 3.8% |
| （別の切り口）手前が塞がって直進では届かない空気 | 13.3% |

詰まり局面で全候補を棄却理由で分類すると（`tools/diag_cause.py`、D03 / D06）、**高さ超過が 96.1% / 88.9%**、扉からの押し込み衝突が 2.8% / 10.5%、支持不足はほぼ0。受理は19万件中12件 / 20万件中0件。

### 対策: 「使えない端材を作らない」（`W_SLIVER`、agents/dev、既定0）

裁断問題の定石。候補を置いたとき、その左右（同じ y 帯・同じ高さ帯）に残る隙間が `GAP+0.012` 〜 `0.20+2*GAP` に入るなら、その幅に比例して減点する。計画型（壁構築・レーン・計画再生。4回とも失敗）と違い、1手ごとの評価の中で完結するので、着地・支持・搬入の判定と衝突しない。候補一括計算（`W_WASTE` と同じ方式）。

**機序は確認できた**（6シーン、W=400）: スリバー 23.6% → **20.8%**、荷物の体積 52.1% → **54.2%**、届かない空気 13.3% → 10.8%。

**しかし配置個数は動かなかった**（64シーン、dense + densetest、対比較）:

| 400 | +0.20 (0.75) | +0.61 (0.61) | 2596 対 2588 |
| 1500（dev のみ） | −1.05 (0.81) | +0.06 | — |
| 5000（dev のみ） | −4.66 (1.26) | −2.36 | — |

**結論: 空けた隙間は「より大きい荷物」に使われ、個数は増えない。** 体積は上がる（fill +0.6、1 se）が個数は横ばい。**横方向の端材は、個数を縛っている制約ではない。** 縛っているのは高さの枯渇（棄却の9割が高さ超過）で、残る低い地面が狭いことは、1手ごとの減点では解消しない。既定OFFで残す。

**次に試すなら**: 減点の対象を「隣の隙間」ではなく「置いた後のスカイラインの平坦部の幅」にする（診断が narrow_col で測っているのはこちら）。ただし候補ごとの計算量が跳ね上がるので、実装は安くない。

**提出候補として作成（2026-09-24、ユーザー判断）**: `tools/make_sliver_variant.py` で `agents/submit` に `W_SLIVER=400` の2か所だけを追加（`packer.py` のみ66行追加、他3ファイルはバイト同一）。出力 `agents/variants/sliver400.zip`（zip sha 213de643deca）。

- preflight `--cpus 4 --load 2`: **PASS**（オフライン最長 149.95s/180s、policy 最長 5.04s、メモリ 81MB）
- 個数は誤差の範囲、fill が1 se 強のプラス。**LB が fill にどう応じるかは未知**（先方の記録では LB と fill の相関は負だった）ので、上振れを期待する提出ではなく、**機序の確認が取れた変更の本番確認**という位置づけ
