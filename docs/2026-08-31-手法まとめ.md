## 0. 結論（3行）

1. この課題は**密度の最適化ではなく「1手も失敗せずに積み切る」生存問題**である。
   1手でも配置NGが出るとエピソードが即終了するため、完走率がスコアを支配する。
2. シミュレータの合否判定は**完全に決定論的な幾何計算**なので、エージェント側で厳密に再実装できる。
   この「実行可能性オラクル」を土台に据えたことが設計上の最大の判断。
3. LB は 21.5 → **27.27** に改善した。伸びの主因は
   **(a) 整定判定の代理オラクル導入**、**(b) 縦置き抑制**、**(c) 左ノッチ帯の到達性改善**、
   **(d) オフライン探索の LNS 化**の4件。

## 1. 問題の構造分析（なぜこの設計にしたか）

### 1.1 支配的な制約は「即死」

`src/ground_handling/env.py` の `step()` は、以下3つのゲートのいずれかを落ちると
`terminated = True` を返す。配置不能な荷物をスキップする手段は存在しない。

| ゲート | 内容 | 我々の対応 |
| --- | --- | --- |
| 内包判定 `is_included` | 7平面すべてに対し内側マージン | `geometry.check_inclusion` で厳密再現 |
| 搬入経路 `is_valid` | 扉から押し込む経路上で1.5cm以内に障害物がないか | `geometry.check_transport_path` で厳密再現 |
| 整定確認 `is_placed_safe` | 300ステップ後に0.3m/45度以上ずれないか | **物理なので厳密再現できない** → 代理指標（§3.2） |

前2つは決定論的な幾何計算なので**厳密に再現でき、無効手を原理的にゼロにできる**。
一方3つ目は物理演算であり、ここだけが本質的に不確実。この非対称性が設計を決めた。

### 1.2 実機検証で見つけた「隠れた仕様」

ソースを読むだけでは分からず、実際に動かして初めて分かった性質。これらは
すべて `geometry.py` に制約として組み込んである。

| 発見 | 内容 |
| --- | --- |
| **縦積みは隙間ゼロで可能** | 搬入経路は最終高さの8cm上を通り、着地の接触は判定されない。一方 X隣接・Y前後は1.5cm超の隙間が必須 |
| **棚上面近傍の即死帯** | 底面zが `[棚上面, 棚上面+0.05]` に入ると持ち上げ量が0になり、真下の支持荷物と衝突して即死 |
| **扉は左が狭い** | `cut_x` 分だけ開口が狭く、左端が-0.51より左の配置はX方向スライドで搬入される |
| **整定ドリフト 1〜1.6cm** | 設計値ではなく**観測姿勢**で毎手再計画しないと後続が失敗する |
| **`env.step` は速い** | `0.012 + 0.015 × 積載数` 秒。8秒予算内に物理検証を10回以上回せる |

### 1.3 スコア構造の理解

README の「手荷物を一定数以上積載できていないと**充填率スコア以外は0**」という条項が決定的。

[`SCORES.md`](SCORES.md) で5指標をローカル実測した結果:

| 指標 | dev 32シーン | ホールドアウト32シーン |
| --- | --- | --- |
| fill_score | 20.6 | 22.2 |
| cog_score | 64.6 | 63.6 |
| stability_score | 29.8 | 26.6 |
| placement_score | 83.9 | 85.6 |
| soft_item_score | 85.5 | 92.3 |
| **5指標の単純平均** | **56.9** | **58.0** |

当時の LB 21.5 は fill_score (20.6〜22.2) とほぼ一致した。
→ **我々は閾値未満で LB = fill_score になっている**という解釈が最も整合的。
→ **cog・placement・soft は既に上位相当。磨いても閾値を跨がなければ1点も入らない。**
→ **最適化すべきは「積載個数」ただ一つ**、という方針が確定した。

## 2. アーキテクチャ

```
agent.py    ── 競技インタフェース（optimize / policy）+ 時間予算管理 + 例外の完全遮蔽
   ↓
packer.py   ── 候補生成（極点＋壁＋グリッド）と多目的スコアリング
   ↓
geometry.py ── 実行可能性オラクル（validator.py の厳密再実装、純Python）
```

**下位層が「合法性」を、上位層が「良さ」を担当する**という分離が設計の核。
オラクルが最終ゲートなので、候補生成はどれだけ雑でも安全 → 探索を自由に設計できる。

### 2.1 `geometry.py` — 実行可能性オラクル（254行）

`src/ground_handling/validator.py` の判定ロジックを numpy 不要の純Pythonで再実装。
コンテナ寸法はすべて実行時に `container_list` から導出し、ハードコードしない
（1〜2コンテナ、棚有無、任意の L/W/H/cut_x/cut_y に対応）。

| 関数 | 対応する本家の判定 |
| --- | --- |
| `check_inclusion` | 7平面の内包判定（斜めカット含む） |
| `check_transport_path` | 扉からの押し込み経路の掃引衝突判定 |
| `resting_eff_start_z` | 持ち上げ量の決定（§1.2 の即死帯を含む） |

安全マージンは仕様値より保守的に取っている（`GAP=0.022` vs 仕様1.5cm など）。
**マージンを仕様値まで詰める実験は逆に悪化した**（§5 却下#3）。整定ドリフトで後続の
搬入が失敗して早期終了するため、保守的な方が価値が高い。

### 2.2 `packer.py` — 候補生成とスコアリング（662行）

**候補生成**は3段階のフォールバック:

1. **極点**（既存箱の辺 ±GAP、壁フラッシュ）— 密に詰まる
2. **壁候補**（[`_infer_walls`](../agents/submit/packer.py) で推論した Y方向の帯の背面エッジ）
3. **グリッド掃引**（極点が候補を出せなくなった時のみ）

高さは列挙せず、**落下着地点モデル**（`_landing`）で (x,y) から導出する。
これは「同一高さの箱の集合を支持レベルとして列挙する」方式が
**19個の箱に対し20個のレベルを生む**という断片化を起こしたため置き換えたもの（§4.1）。

**スコアリング**は多目的の重み付き和。候補は先にスコア順に並べ、
オラクル検証は上位から遅延実行する（=有効候補の真の argmax を、通常は数回の検証で得る）。

| 重み | 値 | 意図 |
| --- | --- | --- |
| `W_LOW` | 400 | 低い位置を優先（重心・支持面の確保） |
| `W_BACK` | 200 | 奥を優先（搬入経路は奥から手前へしか通らない） |
| `W_FLAT` | **600** | **平置きを優先（縦置きの塔を抑制）** ← Day 3 で 100→600 |
| `W_LEFT` | **150** | **左（ノッチ帯）を優先** ← Day 3 で 5→150 |
| `W_ITEM_VOL` | 3000 | プール選択時に大きい荷物を優先（largest-first） |
| `W_MASS_HIGH` | 0.6 | 重い荷物を高所に置かない |

### 2.3 `agent.py` — 競技インタフェース（449行）

- **`policy()` は完全に自己完結**。`observation` から毎回状態を再構築し、`get_init_states`
  で受けた情報に依存しない（policyタイムアウトでプロセスが再起動されると
  `get_init_states` は再送されないため）。
- **例外は完全に遮蔽**しフォールバックを返す（1手の失敗よりタスク全体のクラッシュの方が
  はるかに悪い）。
- 時間予算は本番制限に対し安全マージンを取る（policy 5.0秒/8秒、optimize 150秒/180秒）。

## 3. 現在の結果に至った4つの改善

LB 21.5 → 27.27 の主因。いずれも**測定してから採用**している。

### 3.1 【最大】整定判定の代理オラクル導入

**診断**: 32シーンで再測定した結果、**32/32 のエピソードが `is_valid=False`（探索が候補を
出せず自死）で終わっていた**（[`DIAGNOSIS.md`](DIAGNOSIS.md)）。
真犯人は探索の質ではなく、**`_footprint_supported` が厳しすぎて候補を潰していたこと**。

**変更**: footprint の100%被覆要求 → **静的安定性の判定**へ。

- 重心が接触パッチ上にあるか
- 被覆率60%以上（`SUPPORT_MIN_COVER = 0.60`）
- 荷重重心が footprint 中心から大きく外れていないか（`SUPPORT_CENTROID_TOL = 0.35`）

**効果**: 32シーン norm% **17.8 → 24.1**、積載率 32.6% → 39.7%、**26勝3敗**。

### 3.2 縦置き抑制（`W_FLAT` 100 → 600）

縦に長い姿勢で置くと塔ができ、支持面が細切れになる。平置きを強く優遇。
**効果**: 単体 +1.1。3.1と併せて **17.8 → 25.7、29勝2敗、符号検定 p=4.6e-07**。

### 3.3 左ノッチ帯の到達性（`W_LEFT` 5 → 150）

コンテナ左側のノッチ帯（体積の約23%）は、扉が狭いためX方向スライドでしか到達できず、
**先に右側を埋めると永久に到達不能になる**。左を強く優先することで先に埋める。
**効果**: dev+test 合算 (n=64) で **+2.33pt、38勝18敗、p=0.011**。

### 3.4 オフライン探索の LNS 化

`optimize()` が返せるのは**荷物の到着順序（順列）のみ**だが、これは大きなレバー。
実測で、同一シーンでもランダムな順序は norm% 11.4〜52.0 の幅で振れる。

探索は3段階:

1. 固定4ソートキー（体積・footprint・高さ・質量）
2. GRASP風のランダム重みキー
3. **ruin & recreate（LNS）** ← これが効いた

**なぜ3が必要か**: ソートキーは「4特徴量の重み付け」であり、n! の順列空間のうち
**4次元の部分多様体しか動かせない**。実測でも opt=15秒/60秒/150秒が全て同じスコアで、
その部分多様体は即座に探索し尽くされていた。LNS は順列空間を直接動くので予算に意味が出る。

**効果**: 40シーンオフラインプール **31.72 → 33.43、23勝8敗、p=0.011**。

**これを可能にした前提改修**: rollout の目的関数を「総配置数」から
**プレフィックス長（最初の失敗までの手数）**に変え、**最初の失敗で rollout を打ち切る**ようにした。
実測すると rollout のコストは**ほぼ全部が最初の失敗より後**にあった
（45荷物の rollout 6.6秒のうち失敗前は 0.0秒）。打ち切りで rollout が **10〜30倍安く**なり、
180秒あたりの試行数が約10回から数百回になった。**これが無いと LNS ループは1度も回らない。**

## 4. 開発手法（測定基盤）

「何を作ったか」と同じくらい「どう測ったか」が結果を左右した。

### 4.1 測定基盤のバグを2回踏んだ

| # | バグ | 発覚のきっかけ | 教訓 |
| --- | --- | --- | --- |
| 1 | 壁時計締切による**非決定性**。CPU負荷次第で同一設定の結果が変わる（実測: シーンEで fill 18.2 vs 18.8） | 同一設定を並列実行して差分が出た | 研究用は**決定論的な作業予算**（`MAX_VALIDATIONS`）で走らせ、壁時計はタイミング検証専用に分離 |
| 2 | `tools/harness.py` が import 時に無条件で `agents/submit` を `sys.path` 先頭に挿入し、`--agent-dir` が**黙って無視**されていた | A/B比較3本が全く同じ数値になった | **差が出ないとき、まず測定系を疑う** |

### 4.2 確立した評価プロトコル

1. **決定論モードで測る**（本番モードは品質比較に使わない、タイミング検証専用）
2. **dev プールでスクリーニング → ホールドアウトで最終確認**（別シード）
3. **`norm%`（fill/理論上限）の平均と最悪の両方を見る**（単純合計は高上限シーンが支配する）
4. **符号検定で有意性を確認**（n=32〜64。一部シーンの改善だけで採用しない）
5. **品質とコストを別軸で見る**（品質横ばいでコストだけ増える変更は改善以下）

### 4.3 外部レビューの扱い

最適化の専門家に2度レビューを依頼した。中心的主張（「これは密度でなく到達可能性の問題」
「測定基盤を先に固めろ」）は採用したが、**検証可能な主張のうち3件はソースで裏を取った結果、
誤りだった**。

| 主張 | 検証結果 |
| --- | --- |
| 「マージンを詰めれば0.65m幅が3列入る」 | **誤り**。外寸2.0mで計算していたが内寸は1.92m。0.65×3=1.95で最小マージンでも入らない |
| 「行内は外側X→扉Xの順に埋めるべき」 | **誤り**。荷物は自分自身の目標Xから進入する（`rel_x = clip(target_x,...)`）。X方向の共有廊下は存在しない |
| 「配置不能な荷物をスキップできるか要確認」 | できない。全失敗経路が `terminated = True` |

→ **外部レビューは有用だが、検証可能な主張は必ず自分で裏を取る。**

## 5. 却下した手法（再挑戦しないこと）

**測って捨てた**ものだけを載せる。負の結果も資産である。

| # | 手法 | 結果 | 理由 |
| --- | --- | --- | --- |
| 1 | level-match ボーナス（グローバル版） | fill 122.2→116.9 + 実行時間数倍 | 全コンテナから高さ一致を探すと組み合わせ爆発 |
| 2 | level-match ボーナス（壁ローカル版） | 1シーン+21%だが全体 27.8→26.5 | 一部シーンの改善は全体評価で覆る |
| 3 | 安全マージンの圧縮 | 122.2→116.9 / 105.0 | 整定ドリフトで後続の搬入が失敗し早期終了 |
| 4 | 純粋な層構築スコア（高さ優先を支配的に） | 24.0（壁構築の39.1に大敗） | — |
| 5 | Y候補を壁のみに制限 | 22.9→19.3 | 壁の奥行きに満たない荷物が背面フラッシュにしか置けず手前が死ぬ |
| 6 | GRASP ランダム再スタート200本 | 40シーンで固定4キーと**全シーン完全一致**、135秒を消費 | ソートキーは n! の4次元部分多様体しか動かせない（§3.4） |
| 7 | `optimize` の配置計画を `policy` で再生 | 32シーン 25.7→24.8、オフライン 46.7→38.1 | 計画は**設計座標**で作られ、policy は**整定後の実座標**で走る。再生は情報の多い argmax を少ない argmax に置き換えるので原理的に負ける |
| 8 | オンラインでの生存指標 re-rank | 25.47 → 25.31/24.87/24.65 | 信号が崖まで平坦、かつ探索予算を食う |
| 9 | `irace` によるパラメータ自動調整 | 不採用 | 固定シーンは母集団のサンプルではなく、統計的早期打ち切りの前提が成立しない |
| 10 | **waste ペナルティ**（Wang & Hauser のヒートマップ最小化） | 重み 100/300/600 で -0.78 / -1.20 / **-2.76** と単調悪化 | 空きはスカイライン**下**（占有率85〜93%）ではなく**上**のヘッドルーム（1〜2 m³）にある。減らすべき隙間が無かった |
| 11 | **PyBullet デジタルツインによる整定判定** | 拒否権 dev +0.45 / hold **-0.77**、選好 dev +0.30 / hold -0.35。終了原因の内訳は不変 | ツインは実崩落を 12/12 検出する精度がある。**転倒は詰まりの原因ではなく症状**で、拒否しても死に方が変わるだけ |
| 12 | **プール予算の2パス化**（全部を浅く見てから時間切れ分だけ深く） | 大プールで -0.73 / -0.49 | プールを広く見るより少数を深く見る方が良い |
| 13 | **棚下候補の生成**（`_landing` が棚を支持面として返すので棚の下 0.9m³ が表現不能な件） | 大プール **-2.68**、混合 -0.35 | 棚下は低いので `W_LOW` に好まれて先に埋まり、手前の通路を塞ぐ。空間が見えても使う順序が悪ければ損 |

**設計原則として得られたもの**: 候補生成を「制限」する変更は退行リスクを伴う。
**既存候補への「追加」にすれば構造的に悪化しない**（#5 の失敗と、壁候補を追加形にして
中立に戻した経験から）。

## 6. 現在の弱点と次の一手

### 6.1 弱点

| # | 内容 |
| --- | --- |
| 1 | **積載率が約42%止まり**。閾値を跨げていないため LB = fill_score になっている（§1.3） |
| 2 | **stability_score が 29.8** と5指標中で突出して低い。他4指標は既に上位相当 |
| 3 | 失敗の内訳は 32シーン中 `transport` 24 / `topple` 8。**まだ探索が諦める方が多数派** |
| 4 | 攻め版（LNS）は**分散が大きい**。40シーンでは有意に勝つがサンプル課題000では負ける。これが2本立て提出の理由 |

### 6.2 次の一手

> **2026-09-01 追記: この節の推奨は実装して測って否定された。**
> PyBullet デジタルツイン（`agents/submit/twin.py`）は実崩落を **12/12 検出**する精度に
> 達したが、スコアは動かず（拒否権 dev +0.45 / ホールドアウト **-0.77**、
> 選好 dev +0.30 / ホールドアウト **-0.35**）、終了原因の内訳も不変だった。
> **転倒は詰まりの原因ではなく症状**である。`USE_SETTLE_TWIN = False` で残置。
> 詳細は [`WORKLOG.md`](WORKLOG.md) Day 4。

代わりに Day 4 で効いたのは**計算資源の配分**だった（[`WORKLOG.md`](WORKLOG.md) Day 4）:

- `choose_action` が policy 予算を `pool × containers` で均等割りしており、
  `look_ahead=20` では 1回 0.19 秒に対し `best_placement` は 0.25〜0.35 秒必要。
  全部タイムアウトして「何も置けない」と報告していた（実際には 13543 件の有効配置があった）。
  → `MIN_CALL_BUDGET = 0.8`。dev **+2.37**、ホールドアウト **+2.27**。
- `_landing` を 4.81 倍高速化（意味論不変、90000クエリで出力完全一致）。
  dev +0.44、ホールドアウト +0.45。
- **その結果、計算資源はもう律速ではない**（予算を3倍にしても +0.07）。
  `POLICY_TIME_BUDGET` を上げる意味はなく、上げるのは純粋なリスク。

さらに **Day 4b で `SUPPORT_LIFT = 0.017 < GAP = 0.022` という定数バグ**が見つかった。
棚（および危険帯に入った荷物）の上に置くとき 8cm リフトが 0 になるため、支持面との距離が
持ち上げ量そのものになり、`GAP` 以下だと搬入経路チェックが**必ず**落ちる。
`require_shelf` コンテナの棚面、全コンテナにある小棚、危険帯の荷物の上が丸ごと配置不能だった。
`SUPPORT_LIFT = GAP + 0.008` で **4プール全てで +9〜+16 norm、積載率 42%→59〜62%**。

**現在地: 混合 dev 42.81 / 混合ホールドアウト 46.95 / 大プール 47.78・47.71 / 積載率 59〜62%。**
