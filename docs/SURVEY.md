## 1. 最優先: 先読みプールがほぼ死んでいる

### 1.0 【重要】シーン生成器のバグを修正した

本節の初版を書いた時点で `tools/scenegen.py` は `max_space = look_ahead` としていた。
`max_space` は**プールのサイズではなく補充のトリガ**で、`ItemStreamManager.pop_and_refill` は
`(look_ahead − len(pool)) >= max_space` のときだけ補充する。
つまり `max_space = k` だと**プールが空になるまで補充されない**（バッチ方式）。
実際の `configs/sample_config.json` は**両課題とも `max_space = 1`**、
すなわち1個置くたびに補充される**スライディングウィンドウ**である。

→ `max_space = 1` に修正して全プールを再生成し、以下は**すべて修正後の再測定値**。
結論は定性的に変わらなかった（プールの価値 +2.81 → **+2.85pt**、
害のあるシーン 4/16 → **3/16**）。出荷版の dev 32シーン基準値も 28.42 → **28.30** とほぼ同じなので、
これまでのA/B結論（両群とも同じシーンで比較していた）は無効化されない。

### 1.1 実測（修正後）

`look_ahead > 1` の16シーンについて、**同じシーンで先読みを 1 に落として**比較した
（`tools/scenes_pool_k1.json`）。

| | 平均 norm% | 平均積載率 |
| --- | --- | --- |
| 本来の先読み（k = 3〜20） | 29.73 | 39.3% |
| **強制的に k=1** | 26.87 | 37.8% |
| 差 | **+2.85pt** | **+1.45pt** |

**k が最大20あっても、選択の余地の価値はわずか +2.85pt しかない。**
さらに、**16シーン中3シーンでは k=1 の方が良かった**:

| シーン | k | 先読みあり | k=1 | 差 |
| --- | --- | --- | --- | --- |
| P12 | 10 | 19.26 | 32.14 | **−12.87** |
| P00 | 20 | 33.72 | 41.98 | **−8.26** |
| P31 | 5 | 38.16 | 41.77 | −3.61 |

また **k が大きいほど価値が小さい**（k≥10 の8件で平均 +0.88、k<10 の8件で +4.83）。
選択肢が増えるほど得が減るのは、選択則が情報を使えていない徴候。

**選択肢が20個ある状態が、選択肢1個の状態に10ポイント以上負けるのは論理的におかしい。**
k=1 の挙動は k=20 で常に再現できる（先頭の荷物を選べばよい）のだから、
**現在のプール選択則が積極的に有害**だということになる。

原因は `packer.choose_action`。プールの各荷物について `best_placement` を呼び、
`位置スコア + W_ITEM_VOL × 体積` が最大のものを選ぶだけである。
つまり**「今この1個をどこに置くと気持ちいいか」しか見ておらず、
「この k 個をどういう順で捌くか」を一度も考えていない**。
大物優先（`W_ITEM_VOL`）は「小物から消費して大物が行き場を失う」現象への対症療法であって、
先読みを使っているわけではない。

### 1.2 文献の裏付け

- [DeepPack3D](https://www.sciencedirect.com/science/article/pii/S2665963824001209)（2024）:
  **バッファを 1 → 5 に増やすだけで空間利用率 +7.96%**、処理時間はほぼ横ばい。
- [Online 3D Bin Packing RL Solution with Buffer](https://arxiv.org/abs/2208.07123)（IEEE 2022）:
  バッファによる**複数アイテムからの選択**が行動の自由度を上げ、より良い方策を可能にする、が主張の核。
- [DRL for online 3D-BPP with bin replacement](https://www.sciencedirect.com/science/article/abs/pii/S0166361524001301)（2025）:
  **先読み個数が少ないほど DRL とヒューリスティクスの差が大きい**。裏を返せば
  先読みが多い状況は素朴な手法でも取りに行きやすいということ。

我々は k が大きい状況をむしろ**損**にしている。ここが最大の伸びしろ。

### 1.3 具体的な打ち手

`choose_action` を「1個ずつ独立に評価して argmax」から
**「プールに対する深さ2〜3の先読み」**へ。

```
現在:  for item in pool: score(item) → argmax
提案:  上位 m 個（m=3〜4）に絞り、それぞれ仮に置いた状態で
       残プールの上位数個に対する best_placement の成否・スコアを1〜2手先まで評価
```

コスト試算: `best_placement` は空きがある局面では速く、詰まってから高くなる
（`RESEARCH.md`: 45荷物のロールアウト 6.6秒のうち**最初の失敗までは 0.0秒**）。
深さ2で m=4、残プール上位4個なら追加 16 回程度。policy 予算5秒に対して現実的。
**まず深さ2から測ること。**

[`GAMEPLAN.md`](GAMEPLAN.md) §1.4 で棄却した「生存指標による re-rank」とは別物である点に注意。
あれは**同じ荷物の置き場所**を並べ替える話で効果がなかった。
こちらは**どの荷物を選ぶか**という、実測で +2.8pt しか使えていない自由度の話。

### 1.4 【実測】施策1の効果見積もり — 3つ試して3つとも負け

「深さ2〜3の先読み」を実装して測った。**期待に反して、いずれも改善しなかった。**
すべて `look_ahead>1` の16シーン、現行ルールの基準は norm **29.73**。

| 版 | 内容 | norm% | 対 現行 |
| --- | --- | --- | --- |
| 現行 | プール各荷物の最良スコアの argmax | **29.73** | — |
| 深さ2（m=3, r=4） | 上位3個を仮置きし、残プール上位4個がまだ置けるかを数える | 29.32 | −0.41 |
| 深さ2（m=4, r=6） | 同上、幅を広げる | 29.66 | −0.07 |
| ロールアウト（m=3） | 上位3個を仮置きし、**残プールを最初の失敗まで貪欲に流して prefix 長を比較** | 25.77 | **−3.96** |
| ロールアウト（m=5） | 同上 | 26.90 | −2.83 |

失敗の理由は測定から説明がつく。

- **深さ2**: 「次に置けるか」は崖の直前まで平坦で、判別力が必要なところで差が出ない。
  [`GAMEPLAN.md`](GAMEPLAN.md) §1.2 で測った「生存型数は死の直前まで 7/7 のまま」と同じ現象。
- **ロールアウト**: プールの残り（高々 k−1 個）を流し切っても大半が置けてしまい prefix が飽和する。
  さらに予算の60%をロールアウトに割くので基本探索が浅くなり、その損が上回る。
  オフラインの LNS で prefix が効いたのは**全荷物**を流していたからで、
  プール内だけでは地平線が短すぎる。

### 1.5 では、プール選択にどれだけの価値があるのか（上限の推定）

「どの荷物を選ぶか」**だけ**をランダム化し（配置は貪欲のまま）、8シードで回した。

| | 16シーン平均 norm% |
| --- | --- |
| k=1（プール無効） | 26.87 |
| 乱択（8シードの平均） | 26.90 |
| **現行ルール** | **29.73** |
| 乱択 best-of-2 | 29.03 |
| 乱択 best-of-4 | 32.48 |
| 乱択 best-of-8 | 35.25 |
| ［論理的な床］害を出さないだけ（シーンごとに max(現行, k=1)） | 31.29 |

読み取れること:

1. **乱択の平均 (26.90) は k=1 (26.87) とほぼ同じ**。現行ルールはそれを +2.85pt 上回っており、
   **壊れてはいない**。「プールが有害」は3シーンでの現象で、平均としては正しく機能している。
2. **1シーン内で「どの荷物を選ぶか」だけで動く幅は中央値 16.7pt、最大 29.2pt**。
   自由度そのものには大きな価値が確実にある。
3. しかし **best-of-N は N を増やすほど伸び続け（26.5 → 29.0 → 32.5 → 35.3）飽和しない**。
   これは「上限が高い」ことと同時に、**この推定が勝者の呪いで上方に強く偏っている**ことを意味する。
   決定的な方策は事前にどの選択が当たりかを知らないので、この値には届かない。

**結論: 価値は存在するが、短い地平線の評価では取り出せない。**
当たりの選択を事前に見分けるには、プール内で完結しない**長期の価値推定**が要る
（[`GAMEPLAN.md`](GAMEPLAN.md) §4.2B の教師ありハザード回帰）。
施策1を「軽い先読みで取れる大きな伸びしろ」と見積もったのは**誤り**だった。

## 2. 我々が文献より有利な点: 完全な action mask

[Efficient RL of Task Planners for Robotic Palletization through Iterative Action Masking Learning](https://arxiv.org/abs/2404.04772)（2024）は、
パレタイジング RL の最大の障壁を**「行動空間が巨大で大半が実行不能」**とし、
教師あり学習で行動空間を反復的に枝刈りする。
[ML for Multi-Dimensional BPP サーベイ](https://arxiv.org/abs/2312.08103) も、
本問題群は標準 RL ではなく **Constrained MDP（硬制約の充足が必要）**として扱うべきだと明言している。

**我々は `geometry.py` で validator を厳密再現しているので、近似ではなく厳密な実行可能性マスクを既に持っている。**
文献が学習で近似しようとしているものを、コストゼロで正確に持っている。

含意:
- 学習を入れるなら**マスク学習の段階を丸ごと省略でき、サンプル効率は論文値より良くなるはず**。
- 逆に、**マスクだけでは足りない**ことも我々の実測が示している
  （`DIAGNOSIS.md` の通り、実行可能性を正確に判定できても 32/32 で詰まった）。
  価値は「どこが実行可能か」ではなく「**どこに置くと将来も実行可能が残るか**」にある。

## 3. 頑健性: 期待値と最悪ケースの加重和（AR2L, NeurIPS 2023）

[Adjustable Robust Reinforcement Learning for Online 3D Bin Packing](https://arxiv.org/abs/2310.04323):

- 問題意識: 既存 DRL は**平均性能**を最適化するが実運用では最悪ケースが現実に起きる。
  一方、標準の頑健 RL は最悪ケースを重視しすぎて平均性能を落とす。
- 手法 **AR2L**: 目的を**「期待リターンと最悪ケースリターンの加重和」**として定式化し、
  混合ダイナミクスとの関係から性能下界を導いて、方策改善と交互に最適化する。
- 評価に **permutation-based attacker**（敵対的な箱の順序を探索する攻撃者）を導入し、
  DRL・ヒューリスティクス双方の実用的な頑健性を測る。

これは [`GAMEPLAN.md`](GAMEPLAN.md) §2.2 のエントロピック・リスク
`U_λ = −(1/λ) log Σ q_k e^{−λ c_k}`（λ→0 で期待値、λ→∞ で maximin）と**同じ思想**で、
査読付きの裏付けが取れた形になる。

### すぐできること

**評価軸に「最悪順序でのスコア」を足す。**
`tools/order_sens.py` は既にランダム順序を回しているので、
**ランダムではなく最悪順序を探索するモード**にすれば permutation attacker になる。
実測（`RESEARCH.md` §3.2）ではランダム順序だけでも1シーンで 11.4〜52.0 の幅があった。
本番シーンは未知なので、平均だけでなく**敵対的順序での下限**を見る価値が高い。
提出2本の「守り」側（`submit_safe.zip`）の選定基準にもそのまま使える。

## 4. 安定性制約のコストは文献でも同じ規模

[ML for Multi-Dimensional BPP: Literature Review and Empirical Evaluation](https://arxiv.org/abs/2312.08103) の
実験（Cutting Stock Dataset, online 3D-BPP）:

| 手法 | 安定性制約あり | 安定性制約なし |
| --- | --- | --- |
| PCT（学習） | **75.3%** | 82.8% |
| BPPDRL（学習） | 66.0% | — |
| OnlineBPH（ヒューリスティクス） | 62.7% | 67.2% |
| 3DBP（ヒューリスティクス） | — | 68.9% |

1. **安定性制約を入れると PCT は 82.8% → 75.3% と 7.5pt 落ちる。**
   我々が `_footprint_supported` の緩さで苦しんでいるのは文献でも同じ規模のトレードオフであり、
   実装の稚拙さではなく本質的な難しさ。
2. サーベイ自身が **「ML手法の半数以上が物理的安定性を無視している」**と指摘。
   **論文の利用率の絶対値をそのまま目標にしてはいけない。**
3. 学習手法のヒューリスティクスに対する優位は **+10〜15pt** 程度。小さくはないが桁は変わらない。
4. 実務者への提言が **「オフライン計画とオンラインを組み合わせ、予定と違う順で来たら再計画せよ」**。
   これは我々の `optimize` + `policy` + オラクル再検証という構成そのもの。
   `RESEARCH.md` で計画再生が負けたのは構成が悪いのではなく、
   **再生する計画の質が貪欲と同じだったから**である。

## 5. 5指標をどう扱うか

評価は fill / cog / stability / placement / soft の**加重平均で、重みが未知**。

- [Multi-objective 3D Bin Packing strategies through Meta Reinforcement Learning](https://www.sciencedirect.com/science/article/abs/pii/S2405896325011851)（2025）:
  重み分解で決まる複数の部分問題を既存 DRL は柔軟に扱えないと指摘し、メタ強化学習で対応。
- [STEP: Preference-Conditioned RL](https://arxiv.org/abs/2603.07800)（ICRA 2026）:
  **選好ベクトルで条件付けた単一方策**を学習し、推論時にトレードオフを切り替える。
  「密度を落とさずに作業時間を44%削減」。

学習を入れなくても使える転用:

> **スコア関数を重みベクトル `w` でパラメタライズし、`w` を実行時の定数として持つ。**
> 重みが判明したら `w` を差し替えるだけで済み、再チューニング不要。
> 提出2本を**別の `w`** にすれば、[`GAMEPLAN.md`](GAMEPLAN.md) §5.3 の重み同定と
> §5.2 のポートフォリオを同時に満たせる。

`packer.py` は既に重み定数の集合なので、**構造をほぼ変えずにできる**。

## 6. 前回「本命」としたが優先度を下げたもの

### 6.1 EMS（Empty Maximal Space）

[`RESEARCH.md`](RESEARCH.md) §4b の通り。軸平行の箱しかない本問題では
EMS の角と既存 extreme point がほぼ同じ点集合になる。
文献での EMS の優位は**候補数削減**と**学習方策への空き空間の表現**であって、
extreme point が見落とす位置を拾うことではない。
実測でも「3cmグリッドで全 (x,y) を総当たりしても100%が高さ超過」なので、
候補生成をどう変えても解けない。

### 6.2 フルスクラッチの深層強化学習

**引き続き非推奨。**根拠を更新:

| 論点 | 判断 |
| --- | --- |
| 期待利得 | サーベイ実測で heuristic 比 **+10〜15pt**。魅力的だが桁は変わらない |
| 学習コスト | **サーベイ自身が「訓練時間・計算資源・サンプル効率がどの論文にも報告されていない」と指摘**。見積もりが立たない |
| 我々の1エピソード | 10〜30秒。数百万エピソードは物理的に不可能 |
| 汎化 | サーベイは**データセット横断の検証が無い**と明言。本番カタログが違う本課題ではリスクが高い |
| 推論制約 | 8秒 / 12GB / ネット不可。Transformer 級は載せにくい |

一方、**学習済み重みを zip に同梱すること自体は技術的に可能**
（numpy だけで動く小さな MLP なら数十 KB）。
やるなら [`GAMEPLAN.md`](GAMEPLAN.md) §4.2B の**教師ありハザード回帰**
（状態特徴 → 残り配置可能数）を1手先読みの終端価値に使う形が、
費用対効果でも推論コストでも最も現実的。**RL ではなく回帰**である点が重要。

**深さ2でもプール内ロールアウトでも取り出せない**。
取り出すには長期の価値推定が要り、それは「軽い改修」ではなく §7-1 の中〜大規模な作業になる。

現時点で最も費用対効果が高いのは、**§7-2〜4 の軽い施策**（重みのベクトル化、
最悪順序での評価軸追加）である。いずれも工数が小さく、失敗しても損が小さい。
