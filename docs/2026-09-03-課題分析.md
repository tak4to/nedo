# 現状の課題分析（2026-09-03）

## 0. 前提: 測定基盤の信頼性が回復した

`tools/scenegen.py` の2つの系統誤差（コンテナ寸法・荷物の出現頻度）を修正した結果、
**ローカルの合成値が実測 LB とほぼ一致するようになった。**

| | 合成値 |
| --- | --- |
| 修正前のプール | 57.3 |
| **修正後のプール** | **53.9 〜 54.8** |
| **実測 LB** | **53.4** |

修正前は 4ポイント過大評価していた。以後の判断はこの新しいプールを基準にする。
**過去のプールで出した結論のうち、実タスクで直接確認していないものは再検証が必要。**

## 2. 課題の特定

### 課題A【最大】stability が全指標中で突出して低い

| プール | stability | 平均変位 | 5cm超動いた荷物 |
| --- | --- | --- | --- |
| 混合 dev | 24.02 | 0.151m | **25.5 / 36.5 (70%)** |
| 大プール dev | 21.59 | 0.163m | **25.0 / 33.0 (76%)** |
| 棚 dev | 24.50 | 0.149m | **25.1 / 33.5 (75%)** |
| 棚 holdout | 23.58 | 0.151m | **20.8 / 29.1 (71%)** |

他4指標が 30〜87 の中で **22〜25**。平均変位 0.15m は荷物間隙間（2.2cm）の7倍で、
**荷物の 7割以上が動いている**。滑りではなく荷崩れである。

- **期待値**: 5指標平均なので、22 → 60 で **+7.6**。安全域の全設定の合成値の幅（3.4）の倍以上
- **難易度**: 高い。過去に支持条件・質量重み・GAP を振っても動かなかった実績がある
  （ただし**この指標が無価値だと思っていた時期の調査**で、パラメータを振っただけ）
- **未解明**: なぜ崩れるのか（上層か下層か、塔か壁か）を一度も見ていない

### 課題B【survival】探索が諦める死に方が支配的

| プール | transport（置き場所なし） | topple（崩れた） |
| --- | --- | --- |
| 混合 dev | **25 / 32** | 7 |
| 大プール dev | **24 / 32** | 8 |
| 棚 dev | **23 / 32** | 9 |
| 棚 holdout | **30 / 32** | 2 |

修正前のプールでは transport / topple がほぼ拮抗していたが、
**正しい荷物分布では transport が 72〜94% を占める**。積む個数を決めているのはこちら。

重心 0.715〜0.814m に対し最上面は 1.477〜1.491m（天井 1.57）。
**天井まで約 8cm しか残っていない**ので、単純な空間不足ではなく
「上に積める平らな面が残っていない」形の詰まりである。

### 課題C【セグメント】棚ありコンテナが最も弱い

積載率 **50.0% / 50.1%** に対し、棚なしを含む混合・大プールは 58.5〜58.7%。
棚の下 約0.87m³（容器の21%）が `_landing` の設計上そもそも候補にならない。

ただし**棚下候補の追加は実タスクで逆効果**だった（積載率 64.3% → 54.8%、合成値 58.4 → 52.6、
3回反復して同一）。機序は「棚下に埋めるとソフト／優先荷物が埋まり soft が約10下がる」。
→ `USE_UNDER_OVERHANG = False` で撤回済み。**空間が見えないことが問題なのではなく、
使う順序が問題**である可能性が高い。

### 課題D【リスク】閾値の崖

| プール | 積載率 46% 未満のシーン |
| --- | --- |
| 混合 dev | 5 / 32 |
| 大プール dev | 2 / 32 |
| **棚 dev** | **11 / 32** |
| **棚 holdout** | **8 / 32** |

閾値を割ると合成値ではなく fill のみになる（1シーンあたり約 −25）。
**崖の残りは棚セグメントに集中している。**
ただし実タスク2件は 64.3% / 70.7% で十分上にあるので、
**隠しタスクがどちら側にいるかが分からない**のが本質的な問題。

## 3. 難易度と期待値の評価

| 課題 | 期待値 | 難易度 | 根拠の確かさ |
| --- | --- | --- | --- |
| A. stability | **+7.6**（22→60の場合） | 高 | 代理指標の較正が未確認 |
| B. transport | 閾値を跨ぐシーン数に直結 | 中 | 実績あり（本セッションの2勝はどちらもこれ） |
| C. 棚 | 積載率 +8 相当だが合成値は横ばい | 中 | 実タスクで反証済み |
| D. 崖 | 1シーン +25 | — | 閾値の位置が推定値 |

**A の期待値は最大だが、代理指標の較正が未確認なので期待値そのものが不確実。**
B は実績があり確実だが1件あたりの利得は小さい。

## 4. 未解決の不確実性（これが判断を鈍らせている）

1. **`stability` の絶対値が正しいか。** 揺らし方（横 0.3g × 4方向 × 2周期）は完全な推測。
   本番が穏やかなら実際の stability は高く、課題A の空白は存在しない。
   ただし合成値の総和が LB と一致していることは、**総体としては大きくずれていない**弱い証拠
2. **5指標の重みが均等か。** 均等と仮定している
3. **閾値の正確な位置と単位**（積載率か絶対個数か、コンテナ単位か全体か）
4. **隠しタスクが実サンプル課題（易しい）と合成シーン（難しい）のどちら寄りか**

**1〜3 は提出フィードバックの5指標内訳が1回見られれば全て確定する。**
現状はすべての優先順位付けがこの未確認の仮定の上に乗っている。

## 5. 本セッションで確立した作業原則

| 原則 | 根拠 |
| --- | --- |
| **合成プールで検出力、実タスクで妥当性。両方必須** | 棚下候補は合成64シーンで大勝したが実タスクで逆符号。片方だけなら誤った変更を提出していた |
| **評価は合成値と積載率の両方で見る** | 合成値は「積まない」ことでゲームできる（積載率31.7%で合成値60.7） |
| **パラメータ探索より機序の調査** | 本セッション: パラメータ・ヒューリスティクス 0勝23敗、機序調査 2勝0敗 |
| **測定系を先に疑う** | 測定基盤のバグはこれで3件目（壁時計非決定性 → `--agent-dir` 無視 → シーン分布） |
