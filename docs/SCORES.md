# 5指標の実測と、そこから見える最大の伸びしろ（2026-08-31）

LB が 21.5 に対し上位は 50 以上。**その差の説明が測定でついた**ので記録する。

前提: [`DIAGNOSIS.md`](DIAGNOSIS.md) → [`GAMEPLAN.md`](GAMEPLAN.md) → [`RESEARCH.md`](RESEARCH.md) → [`SURVEY.md`](SURVEY.md)

---

## 0. 結論

**充填率以外の4指標は、すでに上位相当の水準にある。**
足りないのは積載個数だけであり、**LB 21.5 と上位 50+ の差は「積載個数の閾値を跨げていない」ことでほぼ説明できる。**

| 指標 | dev 32シーン | ホールドアウト32シーン |
| --- | --- | --- |
| fill_score | 20.6 | 22.2 |
| cog_score | 64.6 | 63.6 |
| **stability_score** | **29.8** | **26.6** |
| placement_score | 83.9 | 85.6 |
| soft_item_score | 85.5 | 92.3 |
| **5指標の単純平均** | **56.9** | **58.0** |
| 積載率 | 42.3% | 42.9% |

**我々の LB は 21.5 で、これは fill_score (20.6〜22.2) とほぼ一致する。**
一方、5指標を等重みで平均すると 57 前後で、これは上位勢の 50+ と同じレンジにある。
README の「手荷物を一定数以上積載できていないと**充填率スコア以外は0**」という条項に照らすと、
最も整合的な解釈は次の通り:

> **我々は閾値未満なので LB = fill_score になっている。上位勢は閾値を跨いでいるので
> 5指標の平均で 50+ が出ている。**

つまり **packing の「質」ではなく「量」だけが足りていない。**
cog・placement・soft は既に十分高く、これ以上磨いても閾値を跨がなければ 1 点も入らない。

## 1. 測定基盤（今回作った）

`tools/scores.py`。ローカルの `evaluator.py` は fill_score と num_placed_items しか実装しておらず、
残り4指標は**一度も測られていなかった**（`WORKLOG.md` 未解決課題#3）。

| 指標 | 実装した代理指標 |
| --- | --- |
| cog_score | 全荷物の質量加重重心高さを容器高さで正規化 |
| placement_score | 優先手荷物が**異種**の下敷きになっている数＋優先コンテナ違反数 |
| soft_item_score | ソフト貨物が**異種**の下敷きになっている数 |
| **stability_score** | **`Container.create_cap()` で扉に蓋をし、横方向 0.3g の加速度を4方向×2周期かけてから整定させ、平均変位から算出** |

`create_cap()` はローカルの runner から一度も呼ばれていない未使用フック。
README の「コンテナを揺らした際に荷物がどれだけ動かないか」に対応する明らかな用途がある。

公式の式ではないので絶対値は当てにならないが、**方向は README の記述と一致**しており、
2つのエージェントの優劣を比較する用途には使える。

`tools/ab.py` が5指標と単純平均を出力するようになった。

```bash
cd tools && ../.venv/bin/python ab.py --scenes scenes_pool.json --tag x --jobs 14
#  == norm%=28.68 fill=20.62 cog=64.58 stab=29.84 place=83.46 soft=85.46 | COMPOSITE=56.79 packed=42.3%
```

### 注意: この平均は「積まない」ことでゲームできる

支持条件を厳しくして積載個数を落とすと、cog・placement・soft は**自動的に上がる**
（空のコンテナは重心が低く、下敷きもゼロ）。実測:

| SUPPORT_MIN_COVER | fill | cog | stab | place | soft | 平均 | 積載率 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 0.60（現行） | 20.3 | 65.5 | 30.5 | 84.2 | 87.5 | 57.6 | **41.0%** |
| 0.80 | 16.1 | 69.0 | 28.2 | 88.5 | 93.0 | 58.9 | 34.6% |
| 1.00 | 13.6 | 71.2 | 27.5 | 94.8 | 96.6 | **60.7** | **31.7%** |

平均は積載を減らすほど上がる。**本番の閾値条項がこれを潰すのであって、
ローカルの平均だけを見て最適化してはいけない。積載率と必ずセットで見ること。**

## 2. stability が突出して低く、しかも動かない

29.8（dev）/ 26.6（holdout）。他が 63〜92 なので明らかに外れ値。
平均変位は 0.10〜0.21 m ＝ 隙間（2.2cm）を大きく超えており、**滑りではなく崩落**が起きている。

ところが、**思いつく限りの手を打っても動かなかった**:

| 変更 | stability | 備考 |
| --- | --- | --- |
| 現行 | 29.8 | — |
| SUPPORT_MIN_COVER 0.60 → 1.00（完全支持） | 27.5 | **むしろ悪化** |
| W_MASS_HIGH 0.6 → 20 / 60（重い荷物を下へ） | 31.2 / 30.6 | ほぼ不変（cog は +2.5 上がる） |
| GAP 0.022 → 0.018（密に詰める） | 28.9 | 不変 |

完全支持でも改善しないので、**個々の荷物の支持条件の問題ではない**。
高さ 1.4m 級の塔が横 0.3g で倒れているのであって、構造そのものが不安定。
天井まで詰めて上から押さえる／塔を作らない、といった**レイアウト全体の性質**を変えないと動かない。
ただし §0 の通り、閾値を跨がない限りこの指標は 0 のままなので、**優先度は積載個数の後**。

## 3. 今回の変更: 諦める前に全部試すラダー

`_fallback_action` に段階的緩和を実装した。根拠は**論理的に損がない**こと:

- 探索が空振りしたとき、従来は無検証の座標を返していた → `env.step` が失敗 → その時点の状態で終了。
- 代わりに**支持条件だけ落とした配置**を返すと、結果は2通りしかない:
  整定が成功して継続するか、`validator.place_item` が変位超過と判定して**その荷物を取り除き**終了するか。
  後者の最終状態は「諦めた場合」と**完全に同一**。
- したがって危険な一手を試すのは**タダのオプション**である。

ラダー: (1) 優先/ソフトの積み重ね制約を緩める → (2) 静的安定性の要求も外す → (3) 最後に無検証座標。
両方の段に**残り予算の全部**を与える（片方に半分ずつ与えたら1シーンで 18→16 個に退行した。
段2は段1が空振りしたときだけ走るので、削る理由がない）。

実測（dev 32シーン）: 積載率 **41.0% → 42.3%**、fill 20.34 → 20.62、norm 28.30 → 28.68。

## 4. 「マージンは触るな」の正体は FLOOR_LIFT だった

`WORKLOG.md` 却下済み#3 は「安全マージンの圧縮は悪化」だったが、当時は**4つの定数を同時に**動かしていた。
1つずつ切り分けた結果:

| 変更（他は据え置き） | norm | 積載率 | 判定 |
| --- | --- | --- | --- |
| 基準 | 28.54 | 42.0% | — |
| `GAP` 0.022 → 0.018 | 29.14 | 43.0% | dev では改善。**ホールドアウトで 29.08 / 40.3% と再現せず → 不採用** |
| `EFFECTIVE_INCLUSION_MARGIN` −0.015 → −0.009 | 28.39 | 41.8% | 中立 |
| `WALL_CLEARANCE` 0.022 → 0.012 | 21.99 | 32.8% | 悪化 |
| **`FLOOR_LIFT` 0.02 → 0.012** | **7.28** | **14.1%** | **これが犯人** |

**`FLOOR_LIFT` は単独で全体を壊す。**「マージン全般が危険」ではなく
「**FLOOR_LIFT だけは絶対に下げるな**」が正しい教訓。`GAP` は犯人ではなかった。

## 5. 測定の再現性（重要）

同一コードを3回走らせた結果:

| | run1 | run2 | run3 |
| --- | --- | --- | --- |
| 32シーン平均 norm | 28.64 | 28.73 | 28.68 |

- **平均は sd 0.04pt で非常に安定** → 平均の差が 0.3pt 以上あれば実体がある。
- **一方シーン別は不安定**: 同一コード2回で **7/32 シーンの積載個数が変わり**、
  シーン別 |Δnorm| は平均 0.63pt・最大 6.74pt。壁時計デッドラインが残っているため。

**含意: 本セッションで報告した「勝敗数と符号検定」は、
2割程度のシーンが偶然で反転する分だけ楽観側に偏っている。**
平均差（例: `W_LEFT` の +2.33pt）は run 間 sd 0.04pt を大きく超えるので結論は保たれるが、
今後は**勝敗数ではなく平均差を主指標にする**こと。
（`WORKLOG.md` §12.2 で作った research モードを捨ててしまったのが原因。復活させる価値がある。）
