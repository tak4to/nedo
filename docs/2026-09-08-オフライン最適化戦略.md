# オフライン最適化（`optimize`）の戦略（2026-09-08）

前提資料: `docs/2026-09-06-戦略まとめ.md`（LB 較正・5指標の構造）。
本書はその「次回の課題」のうち **オフライン側（`optimize`）だけ** を、実測と最新研究の
両方から作り直す。

# 0. 結論（先に）

**現行 `optimize` は、150秒のうち 140秒を無駄にしている。しかも、その 140秒で
「見つけて捨てた」解の中に、無料で取れる改善が入っている。**

実タスク R000（唯一の実オフライン課題、`optimize=True` / `look_ahead=1` / 41個）で
150秒フル回した実測:

| 実測項目 | 値 |
| --- | --- |
| ロールアウト回数 | **820回** |
| 受理された改善 | **4回** |
| 最後に改善した時刻 | **t = 9.7 秒**（残り 140秒は 1回も動かない） |
| 目的値 `prefix_len` の取り得た値 | 19〜30 の **12段階のみ**（＝巨大なプラトー） |
| 到達 prefix 30 の解を何本見たか | **214本** |
| その 214本の cog 代理値の幅 | **48.45 〜 53.05（4.60ポイント）** |
| 現行が返す解の cog | **49.08**（最初に prefix 30 に到達した解） |

**同じ積載個数（30個）で cog を 53.05 にできる順列を、探索は既に見つけていて、
目的関数がそれを区別できないので捨てている。** 差 +3.97 cog = composite +0.79。

さらに、現行の同値解の破り方（`prefix_volume` 降順）は **cog を下げる方向に効いている**
（体積の大きい荷物を先に置く＝高く積む）。つまり今の tiebreaker は無害ではなく有害。

やることは 3行で書ける:

1. **`optimize` が本番で呼ばれているかを提出フィードバックで確認する**（コストゼロ・最優先）
2. **ロールアウトの目的関数を `(prefix_len, prefix_volume)` から
   `(prefix_len, composite代理)` に差し替える**（構造上ぜったいに悪化しない）
3. **受理基準を strict improvement から record-to-record travel に変える**（停滞の解消）

# 1. 【最優先・コストゼロ】そもそも `optimize` は呼ばれているのか

## 1.1 `optimize` はタスクごとの `agent.optimize` フラグで完全に gate されている

`src/ground_handling/app.py:58` が `if env.optimize:` で囲っている。
**フラグが False のタスクでは `optimize()` は一度も呼ばれない。**

## 1.2 実 config では `optimize` と `look_ahead` が結合している

| task | `agent.optimize` | `look_ahead` | 荷物数 |
| --- | --- | --- | --- |
| 000 | **True** | **1** | 41 |
| 001 | **False** | **10** | 42 |

課題設計として自然な形（全順序が事前に見える代わりに窓は1個 / 窓はk個だが事前情報なし）で、
**2件とも「オフライン ⟺ k=1」「オンライン ⟺ k大」で綺麗に対になっている。**

ここに矛盾がある。メモリ（`nedo-baggage-competition`）で確定させた
**「本番タスクは `look_ahead` が大きい」**（`MIN_CALL_BUDGET` の効果が k=1 で +0.12 /
k=20 で +13.36、かつ LB が +26 動いた）と、上の結合を合わせると、

> **本番タスクの大半は `look_ahead` が大きい → 結合が成り立つなら大半は `optimize=False`
> → `optimize()` はほとんど呼ばれていない。**

これが正しければ、`optimize` に注ぐ工数の期待値はゼロに近い。逆にこれが誤りなら
（＝結合が2件の偶然で、本番には高kのオフライン課題がある）、`optimize` は
**180秒＝policy 1回の 22倍の計算資源を持つ最大の未開拓リソース**である。

**どちらであるかは、提出フィードバックの1フィールドで確定する。**

## 1.3 確定させる方法（工数ゼロ）

提出フィードバックの `time_results.optimization`（全タスクに対する **最大値**）を見る。

- 現行エージェントは `OPTIMIZE_TIME_BUDGET = 150.0` で、呼ばれれば必ず 150秒使い切る
  （本日の実測 wall 149.9s）。
- したがって:

| `time_results.optimization` | 判定 |
| --- | --- |
| **≈ 150** | オフライン課題が本番に存在する → 本書の施策はすべて有効 |
| **≈ 0** | **本番に `optimize=True` のタスクが1つも無い** → 本書は破棄。2枠が `OFFLINE_SEARCH` しか違わないのも無意味（同一挙動）だったことになる |

LB 55.12 の提出フィードバックにこの値が入っている。**まずこれを読むこと。**
（課題4「提出ポートフォリオが分散していない」の答えも同時に出る。`submit.zip` と
`submit_safe.zip` は `diff` を取ると **`OFFLINE_SEARCH` の1行しか違わない**ので、
オフライン課題が無ければ2枠は完全に同一のエージェントである。）

## 1.4 測定基盤のバグ 4件目: シーン生成器が (optimize, look_ahead) を独立サンプリングしている

`tools/poolgen.py:12-13`:

```python
look_ahead=rng.choice([1,1,3,5,10,20]),
offline=rng.random() < 0.4,
```

**独立に振っている。** 結果として既存プールの内訳は

| プール | `(optimize=True, k=1)` の数 |
| --- | --- |
| `scenes_pool` (32) | **1** |
| `scenes_k` (30) | **0** |
| `scenes_shelf` (32) | **0** |

一方で `(True, k=20)` や `(True, k=40)` という **実 config には存在しない組み合わせ**を
測っている。しかもこの2つは `rollout` の意味論そのものを変える:
`allowed_misses = max(1, lookahead_k)` なので、k=1 では「最初の失敗で停止」、
k=20 では「20回失敗するまで続行」——**別のアルゴリズムを測っていることになる。**

これは 2026-09-03 に踏んだ「シーン生成器の分布が実タスクと違う」の
**同じ罠の4件目**である。

→ **`tools/scenes_off.json`（`offline=True, look_ahead=1`、実寸法・実カタログ重み、64シーン）
を作る。** `poolgen.py` の2行を固定するだけ。これが無いと、以下のどの施策も
検出力ゼロで測ることになる（現状オフライン regime の実シーンは **R000 の1件だけ**）。

# 2. 現行アルゴリズムの解剖（実測）

## 2.1 構造

`optimize` が返せるのは**順列ひとつだけ**。探索は3段:

1. 固定ソートキー4本（volume / footprint / height / mass）
2. ランダム化ソートキー最大8本（GRASP）
3. incumbent への ruin-and-recreate（LNS）— 残り時間すべて

評価は `rollout()`: 順序を貪欲に流し、**最初の失敗で打ち切って**
`(置けた個数, 置けた体積)` を返す。受理は `if key > best_key` の **strict improvement のみ**。

**サロゲートの精度は良い。** R000 で rollout が到達した prefix は **30**、
実機実行の積載個数も **30個**（41個の 73.2%）で一致する。
つまり「順序 → 積載個数」の予測は当たっている。問題は探索と目的関数の側にある。

## 2.2 欠陥（実測で確認したもの）

### D1. 目的関数が LB と別のものを測っている ← 最大

`(prefix_len, prefix_volume)` は **積載個数と充填率**を最大化する。
しかし較正で確定した事実は:

> B → C で fill +16.6 / 積載率 +26.5pt 動いたのに **LB は +1.72 しか動かない**。
> 残る余地は **stability と cog の2つだけ**。

**探索が最大化している量は、LB が既に飽和している量である。**

さらに悪いことに、同値解の破り方 `prefix_volume` 降順は
「大きい荷物を先に置く＝高く積む」＝**cog を下げる**方向に働く。
実測でも prefix が伸びるほど cog は下がっている:

| rollout の prefix | cog 代理（平均） |
| --- | --- |
| 23 | 54.02 |
| 26 | 53.71 |
| 28 | 51.74 |
| **30** | **49.10** |

これは「CEM 前は cog 63.7 だったのが 51.6 に落ちた」という既知の副作用と同じ現象が、
オフライン探索の内部でも起きているということ。

### D2. 目的値が整数なので探索面がプラトーで、strict improvement では動けない

`prefix_len` は 19〜30 の **12段階しか取らない**。
n=41 の順列空間 (41! ≈ 3.3×10^49) に対して目的値が 12値。
**strict improvement のヒルクライムは 9.7秒で頂上に着き、以後 140秒・約750回の
ロールアウトが1回も受理されない。**

ALNS の受理基準を横断比較した Santini, Ropke & Hvattum (2018) の結論は明快で、
**simulated annealing / threshold acceptance / record-to-record travel の3つが
上位グループを占め、なかでも record-to-record travel が一貫して劣位に立たない**。
現行の strict improvement はこの比較の対象にすら入らない（＝下位）。

### D3. ロールアウト間でプレフィックスを共有しているのに毎回作り直している

LNS の再挿入は「元の位置の近傍」に限定しているので、新しい順列は incumbent と
**先頭を共有する**。実測: **incumbent との最長共通接頭辞は平均 21.4 / 41（中央値 25）。
全ロールアウトの半分以上が、同一のシミュレーションの再計算である。**

ToP（後述）は「隣接ステップの MCTS が同じパスを共有するのでグローバルキャッシュを持つ。
これで決定時間がほぼ半減する」と報告している。同じ構造がここにある。

**ただし正直に言うと、ここの利得は 2.1× より小さい。** `best_placement` は
「空きがあるうちは安く、詰まると高い」（`agent.py` のコメントにある実測）ので、
キャッシュできるのは**安い前半**である。実装前に「prefix 21 までの所要時間 /
全体」を測ってから判断すべき。優先度は下。

### D4. 「GRASP を測ったらゼロだった」は BRKGA を否定していない

`docs/STRATEGY.md #12.6` と `agent.py` のコメントは
「ランダム化ソートキー 200本は fixed とバイト単位で同一の答えを返した」と記録している。
これは正しいが、**理由は「多スタートが効かない」ではなく「4次元しか動かせない」**である
（`make_random_key` は volume / footprint / height / mass の**4つの重み**を振るだけなので、
到達できるのは n! の中の4次元部分多様体だけ）。コメント自身がそう書いている。

**BRKGA（biased random-key GA、Gonçalves & Resende が container loading に適用して以来
この問題クラスの定番）が振るのは「荷物ごとに1つ、計 n 個のランダムキー」であって、
ソートすれば n! 全体に到達できる。** 我々が測ってゼロだったものとは別物であり、
却下の根拠にならない。

### D5. サロゲートと実機のギャップに対して無防備

`agent.py:55-60` が自ら記録している:

> 'lns' はプールでは勝つが分散の大きい賭け。ロールアウトの prefix 長を最適化するが、
> ロールアウトはドリフトが無く実機にはある。**サンプル課題000では 6ポイント損している。**

これは典型的なサロゲート過適合であり、対処法は文献的に確立している
（ロバスト最適化／シナリオサンプリング）: **公称値ではなく、摂動を入れた複数ロールアウトの
平均あるいは CVaR で順列を評価する。**

現行手法がどこに位置し、何が欠けているか。

| 研究 | 何を言っているか | 我々への含意 |
| --- | --- | --- |

**要約: 我々のアルゴリズムの「骨格」（順序探索 × 固定配置方策）は 2025 年の SOTA と同じ。

# 4. 施策（優先順）

すべて `agents/submit/agent.py` の `optimize()` 内で完結し、`policy` には触らない。
**`policy` に触らない = オンライン課題のスコアは構造的に不変**なので、
オフライン課題が本番に存在する限り、下振れリスクは提出枠のリスクのみ。

## O0. 【工数ゼロ・最優先】提出フィードバックの `time_results.optimization` を読む

§1.3 の通り。**≈0 なら本書は破棄して policy 側に全振りする。**
同じフィードバックの5指標内訳が、`docs/2026-09-06-戦略まとめ.md` の課題2・課題3も同時に解く。

## O1. 【最大・構造上悪化しない】ロールアウトの目的関数を composite 代理に差し替える

### やること

`rollout()` の戻り値を

```python
return (len(ordered), prefix_volume), ...
```

から

```python
return (len(ordered), composite_proxy(states, ordered)), ...
```

に変える。**第1項（積載個数）はそのまま残す。** 変えるのは同値解の破り方だけなので、
返る順列の積載個数は絶対に減らない（＝閾値割れのリスクがゼロ）。
これは既存の設計原則「候補生成を『制限』せず『追加』の形にする」と同じ構え。

### `composite_proxy` に何が入るか

**5指標のうち4つは、ロールアウトの終端状態からほぼ厳密に計算できる。**

| 指標 | ロールアウトから計算できるか | 方法 |
| --- | --- | --- |
| `fill_score` | ○（現行の `prefix_volume` そのもの） | 体積和 / コンテナ体積 |
| `cog_score` | **◎ 厳密**（`tools/scores.py:25` と同じ式） | `100·(1 − Σm·z/Σm / H)`。`ContainerState.boxes` に質量も z もある |
| `placement_score` | ○ | 優先荷物の上に非優先が載っているかは箱の重なりで判定できる |
| `soft_item_score` | ○ | 同上 |
| `stability_score` | △（O6 で別途） | 静的代理（支持多角形マージン、重心の高さ、接触グラフ） |

`tools/objective.py` に既にある `smooth_objective`（ロジスティック傾斜版）を
**そのままエージェント側に移植する**のが筋。報告用の階段版ではなく smooth 版を使う
（`docs/2026-09-06-戦略まとめ.md`「次回 CEM を回すときの設計指針」1と同じ理由）。

### 効果（実測に基づく下限）

R000 で **現行の探索が既に訪れた 214本の prefix=30 の解**の中で:

- 現行が返す解: cog **49.08**
- 同じ prefix=30 で最良: cog **53.05**
- **差 +3.97 cog = composite +0.79**

これは「新しく探索して見つける」必要すらない、**目的関数を直すだけで拾える下限**である。
探索が停滞を解けば（O2〜O4）上振れする。

**LB 換算**（較正ルールに従う）: 実タスク composite → LB は係数 **0.76**。
オフライン課題の本番比率を f とすると **ΔLB ≈ 0.76 × 0.79 × f ≈ 0.6f**。
f=0.5 なら **+0.3**。**小さい。** 正直に書いておく。
上振れ余地は (a) 探索改善で cog 幅が 4.60 より広がる、(b) 同じ並べ替えが
stability も持ち上げる（低く平らに積むので方向は一致する）、の2つ。

## O2. 受理基準を record-to-record travel にする

### やること

`offer()` の `if key > best_key:` を、**best とは別に current を持つ**構造に変える。

```python
# best は記録用（最後に返す）。current は探索の現在地。
if key > best_key:
    best_key, best_order, best_plan = key, order, plan
if key >= threshold(best_key):        # record-to-record travel
    cur_key, cur_order = key, order   # 悪化していても現在地を移す
```

`threshold` は record（＝best）からの許容劣化幅。RRT の標準形は
`best − dev`（dev は best の数%）。ここでは第1項が整数なので
「prefix は best−1 まで許容、composite 代理は自由」から始めるのが素直。
LNS の破壊対象は `best_order` ではなく `cur_order` にする。

### 効果

**140秒 / 約750ロールアウトが現在ゼロ産出。** これを使えるようにする。
定量的な事前予測はしない（`docs/2026-09-06-戦略まとめ.md` の較正ルール）。

**注意: O1 を入れると O2 の必要性は下がる。** composite 代理は連続値なので
プラトーが解け、strict improvement でも動けるようになる。
**O1 → 測定 → O2 の順にすること。** 逆順だと O2 の効果を過大評価する。

## O3. 【条件付き】プレフィックスキャッシュ

incumbent と共有する接頭辞（実測 平均 21.4 / 41）の `ContainerState` をスナップショットして
再利用する。`ContainerState` は `__slots__` + 箱の dict リストなので、
浅いコピー + `_refresh()` で足りる（箱は commit 後に変更されない）。

**先に測ること**: 「先頭 21個ぶんのロールアウト時間 / 全体」。
`best_placement` は詰まってから高くなるので、**キャッシュできるのは安い側**であり、
利得は 2.1× より小さいはず。この比が 0.3 未満なら実装する価値は薄い。

## O4. 多様化を BRKGA（n次元ランダムキー）に置き換える

現行の `make_random_key`（4重みのランダム化、上限8本）を、
**荷物ごとに1つのランダムキー**を持つ本来の BRKGA デコーダに置き換える。
文献の定石通り LNS とハイブリッドにする（BRKGA で母集団を保ち、
エリート個体に ruin-and-recreate をかける）。

「GRASP を測ったらゼロだった」は §D4 の通りこの施策を否定しない。
ただし **CEM で 14重みを同時最適化した経験（`docs/2026-09-06-戦略まとめ.md`）と同じ罠**
——単独A/Bの検出力不足——があるので、**O1・O2 を入れた後の土俵で測る**こと。

## O5. サロゲートのロバスト化（摂動ロールアウト）

`agent.py` 自身が記録している「lns はサンプル課題000で6ポイント損する」への処方箋。

**やること**: 順列を1本の公称ロールアウトで評価するのをやめ、
`commit` する着地高さに小さなドリフト（実測の整定ドリフトは 1〜2cm）を注入した
**m本（m=3）のロールアウトの平均、または下側（CVaR）** で評価する。

コストは m 倍。O1〜O3 で稼いだ予算をここに使う形になる。
**`OFFLINE_SEARCH='lns'` が攻め枠であることの本質的な理由（分散）を潰す施策**なので、
成功すれば2枠を分散させる必要自体が減る。

## O6. stability の静的代理を目的関数に足す

**期待値は最大、確度は最低。** stability は5指標中唯一 21〜25 で、22 → 60 なら +7.6。
ただし揺らし方（横 0.3g × 4方向 × 2周期）は完全な推測。

- LBCP（arXiv 2507.09123）の考え方——**支持多角形の内側にどれだけ余裕をもって重心が乗るか**
  ——を静的特徴として `composite_proxy` に足す。物理シミュレーション不要。
- `twin.py`（PyBullet、実崩落 12/12 検出）は online では中立だったが、
  **`agent.py` 自身が「オフラインの配置レベル探索なら1決定あたりずっと多く回せる。これは別の賭けだ」
  と書いて残してある。** 150秒あれば終端状態に対して数十回の shake が回せる。

**O0 で5指標内訳が取れるまで着手しない。** 較正なしに揺らし方を推測するのは
`docs/2026-09-06-戦略まとめ.md` 課題2 そのもの。

## O7. 提出ポートフォリオ

O0 の結果次第:

- **オフライン課題が存在する場合**: 現行の `lns` / `fixed` の2枠は
  「同じ目的関数の探索強度違い」でしかない。O1 後は
  **`lns + composite目的`（攻め）と `fixed`（守り）** にする。
- **存在しない場合**: 2枠が完全同一なので、片方を積載率重視に振る
  （`docs/2026-09-06-戦略まとめ.md` 課題4）。コストゼロ。

## O1: `packer.pack_metrics`

5指標のうち **4つはロールアウトの終端状態から計算できる**。実装して実機 R000 の

| 指標 | 実測 | 代理 | 差 |
| --- | --- | --- | --- |

**cog / placement / soft は完全一致。** fill だけ系統的に過大だが、これは公式 fill が

## O2: record-to-record travel

`best_*`（記録）と `cur_*`（探索の現在地）を分離し、
`items × RRT_ITEM_WORTH + composite ≥ 記録 − RRT_DEV` を満たす解に現在地を移す。
ruin-and-recreate は `cur_order` を壊す。`RRT_DEV = 1.0` は
**1つの個数レベル内で観測された composite の広がり（約1.5）のすぐ下**に置いた
——ランダムウォークにはせず、プラトーは横断できる幅。
`RRT_ITEM_WORTH = 10.0` は「積んだ1個を手放すのは事実上拒否」を意味する。

## O3: プレフィックス再開（ToP のパスキャッシュに相当）

ロールアウトが各位置での状態スナップショット列（trail）を返し、次の試行は
共通接頭辞の位置から再開する。`ContainerState.clone()` は `boxes` だけ複製し、
派生ビュー（`floor_boxes` / `landing_index`）は `_refresh` が丸ごと差し替える設計なので
**共有したまま**にできる。結果、スナップショット1つが O(箱数)・ソートなし。

**採否ゲートの実測（`probe_opt.py`）**: 共通接頭辞は
**荷物の 64% ／ ロールアウト時間の 60%**。当初「キャッシュできるのは安い前半なので
2.1倍より小さいはず」と書いたが、**実際はほぼ比例していた**（最良ケース 2.48倍）。
戦略段階の見立てが外れた側なので記録しておく。

**意味論不変の検証（`tools/check_resume.py`）**: 再開したロールアウトを毎回
**ゼロからもう一度回して `(key, order, plan)` をバイト比較**する。R000 で
**27/27 完全一致**。`_landing` 4.81倍高速化のときと同じ基準。

## 三段の測定（検出力・転移・妥当性）

実行時間: policy 最大 0.57s / 3.98s（制限 8s）、optimize 150s（制限 180s）。

**LB 換算**（較正ルール）: 合成プールは 3〜4倍過大、実タスクは 0.76倍。

## 却下した2件と、その理由

### RRT（record-to-record travel）: composite −0.68 (se 0.55)

停滞そのものは実在した（820ロールアウト / 受理4回 / 最後 t=9.7s）。
しかし**プラトーを横断できないことが探索の不足ではなかった**。
目的関数がプラトー上の解を区別できるようになった時点で、strict improvement のままでも
そこへ到達する。歩みを下り坂に許すぶんは積載個数の損（−0.49pt）にしかならなかった。

### プレフィックスキャッシュ: 実タスクで −6.4 composite

接頭辞が荷物の 64% / 時間の 60% を占めるのも、ロールアウトが増えるのも本当で、
**意味論不変も証明した**（`check_resume.py`、60/60 バイト一致）。それでも:

| | Δcomposite |
| --- | --- |
| 64シーン・旧目的関数 | −0.64 (se 0.52) |
| 64シーン・新目的関数 | +0.42 (se 0.39) |
| 実タスク R000・旧目的関数 | ±0.0（順序が完全に同一） |
| 実タスク R000・新目的関数 | **62.2 → 55.8** |

プール側はどちらも自身の標準誤差を超えない。実タスクは決定論的で、
**optimize 予算 140 / 150 / 160秒で完全に同一の結果**（＝不安定シーンではない）。

**純粋な予算最適化に「答えを良くする」理屈は無い。** できるのはプラトー上の
別の場所へ探索を動かすことだけで、R000 ではそこが悪かった。
ロールアウトが実機の偏りの無い予測子になれば（O5）話は変わるので、スイッチは残した。

## 予想が外れたところ（3件）

| 予想 | 実際 |
| --- | --- |
| 効くのは **cog**（R000 で幅 4.60 を実測） | **placement +5.91 / soft +3.55**。cog は +0.03 で動かない。到着順序が支配するのは「優先/ソフト荷物の上に別クラスが載るか」だった |
| 効果は composite +0.79 | 開発 +1.26 / ホールドアウト +1.37 / 実タスク **+3.2** |
| キャッシュできるのは安い前半なので 2.1倍未満 | 荷物 64% に対し時間 60% で**ほぼ比例**（最良 2.48倍）。ただし採用には至らず |

## 副産物: `fixed` モードは composite の蜃気楼

LNS を切ると composite は **+2.61**（全アーム中最大）だが、積載率が **−5.41pt** 落ち、
**6シーンが閾値を割る**。閾値モデルでの estLB は **−0.17**。
`tools/objective.py` の警告（「composite は積まないことで最大化できる」）そのもので、
composite だけを見ていれば誤って採用していた。**採否は必ず閾値モデルで見ること。**

なお `fixed` モードでは新旧の目的関数がバイト単位で同一の結果を返す
（固定4キーが prefix 長で並ぶことが無く、タイブレークが発火しない）。
**目的関数は、向ける先の探索があって初めて効く。**

## 残った弱点

`pack_metrics` は5指標のうち **stability だけ計算できない**（物理が要る）。
つまり探索は stability を無償で売り払える。実測では
ホールドアウト +1.57 / R000 −1.2 で系統的な害は出ていないが、構造としては残る。
→ **O6（LBCP 型の静的安定性代理）の根拠がこれ。ただし O0 が先。**

# 第2ラウンド（2026-09-09）: `optimize` は本番でも呼ばれると判明

O0 の答えが出た（本番でも `optimize` は呼ばれる）ので、実タスク +3.2 がそのまま期待値に効く。
「他に手法は無いか」を、**手法を選ぶ前にサロゲートの忠実度を測る**という順序で調べた。

## 測定1: ロールアウトは何を予測できているのか（`tools/surrogate_fit.py`）

64シーンで「ロールアウトが言う値」と「実際に走らせた値」を突き合わせた。

| 量 | 予測 | 実際 | バイアス | r（**シーン間**） |
| --- | --- | --- | --- | --- |
| 積載個数 | 39.0 | 39.0 | +0.0 | **0.978** |
| composite | 69.71 | 68.33 | +1.38 | 0.521 |

## 測定2: 探索が実際にやること — シーン**内**の順序比較（`tools/order_fidelity.py`）

探索は2つのシーンを比べない。**同じシーンの2つの順序**を比べる。
そこで12シーン×10順序で、シーン内の順位相関を測った。

| | シーン間 | **シーン内** |
| --- | --- | --- |
| 積載個数 | r = 0.978 | **ρ = +0.474** |
| composite | r = 0.521 | **ρ = +0.273** |

**ロールアウトは難しいシーンと易しいシーンを見分けるのは得意で、
同じシーンの良い順序と悪い順序を見分けるのは苦手だった。** 探索は後者しかやらない。

→ **この時点でビームサーチ（当初の第1候補）を撤回した。** ρ=0.27 の上で候補を増やす手法は、
ノイズを丁寧に並べ替えることにしかならない。

## 測定3: ずれの正体（`tools/drift_fit.py`）

要求座標と整定後の実座標を 637配置ぶん測った。

| 軸 | 平均 | sd | \|d\| p50 | p90 | p99 |
| --- | --- | --- | --- | --- | --- |
| dx | +0.0003 | 0.0058 | 0.0001 | 0.0010 | 0.0107 |
| dy | −0.0001 | 0.0037 | 0.0001 | 0.0013 | 0.0085 |
| **dz** | **−0.0118** | 0.0158 | 0.0002 | **0.0300** | 0.0650 |

**横にはずれない。沈むだけ。** しかも剛体荷物の分位点は
`[~0, ~0, ~0, ~0, ~0, ~0, ~0, 0.020, 0.030, 0.030]` ——
**7割は動かず、3割がちょうど 0.020 か 0.030 沈む。**
これは物理ノイズではなく `FLOOR_LIFT = 0.020` と `SUPPORT_LIFT = 0.030` そのものである。

`_bottom_for_support` は搬入経路の掃引が支持面を削るのを避けるため、荷物を支持面の
3cm 上に浮かせて置く。評価基盤はそれを落として着地させる。
**ロールアウトは浮かせた高さのまま箱を記録し続けていたので、その列の以降の荷物が
すべて 2〜3cm 高い面の上に積まれ、誤差が積み上がっていた。**

## 採用: 着地高さでコミット（`ROLLOUT_SETTLE`）

`_landing` で支持面の高さを引き直して `min(設計高さ, 着地高さ)` でコミットする。
既存のホットパス1回ぶんのコスト（`_landing` は 4.81倍高速化済み）。

# 第3ラウンド（2026-09-12）: 測定設計そのものを測る

## S1【確定】「sd≈5 は処置の異質性」は誤りだった

`docs/2026-09-06-戦略まとめ.md` 課題1 は、対応のある差の sd ≈ 5 を
**処置の異質性**（＝繰り返し測っても減らない）と診断し、そこから
「32シーンでの検出力は8〜20%だが仕方ない」という判断を導いている。
この一文が以後の全A/Bの形を決めていた。

**検証**: 10シーン × 4探索シード × 2アーム = 80ラン（`tools/varcomp.py`）。
差を `d_ij = τ + b_i + e_ij` と書き、`b_i`（シーンの応答）と `e_ij`（探索が
どの局所解に落ちたか）を分離した。

| 成分 | 分散 | sd |
| --- | --- | --- |
| `Var(e)` 探索シード | **35.45** | **5.95** |
| `Var(b)` 真の処置異質性 | **0.00** | **0.00** |

**ばらつきの 100% が探索シードの雑音で、シーン由来の異質性はゼロ。**

1シーンの内訳が全てを語る。O00 は同一シーン・同一処置で
`[+8.6, −9.3, −3.4, +13.5]` と **23ポイント**振れる。

### 3つの帰結

**1. 検出力に下限は無い。** `Var(b)=0` なので se は総ラン数だけで決まり、
シーンとシードは等価である。

| シーン | シード | ラン | se | MDE(80%) |
| --- | --- | --- | --- | --- |
| 32 | 1 | 64 | 1.05 | 2.9 |
| 64 | 1 | 128 | 0.74 | 2.1 |
| 64 | 4 | 512 | **0.37** | **1.0** |
| 32 | 8 | 512 | **0.37** | **1.0** |

過去24件の却下は se ≈ 1.05 の道具で下された。**+1.0 の効果に対する検出力は 17%。**
「効果が無かった」と「見えなかった」は、やはり区別できていなかった。

**2. 「どのシーンで効くか」を探す分析は原理的に無意味。**
シーン記述子10個での効果回帰は leave-one-out R² = **−0.31**（`tools/hte.py`）。
`Var(b)=0` と完全に整合する。条件付き適用・セグメント別チューニングは捨ててよい。

**3. 実タスクが計測器になる。** 単一シーンでも se は `sd/√seeds` で下がる。
R000 は 8シードで se 1.92、36シードで se 1.0。**n=1 の逸話ではなくなる。**

### そして sd 5.95 は邪魔者であると同時に取り逃がしている性能である

毎回この分布から1本引いて、引いたものを出荷している。
**選抜を改善できれば取り返せる幅がここにある** —— どの施策の効果量よりも大きい。
これが S2 の動機と規模を同時に与える。

### 【方法論の誤り】検証の合否基準に ρ を選んだのが間違いだった

着手前に「シーン内 ρ が 0.337 を超えなければ棄却」と宣言した。
settle 300 の判定器は **ρ 0.444 で基準を超えたのに、実益は −0.21** である。

**ρ は候補集合「全体」の順位相関で、選抜が問うのは「上位数本の識別」だけ。**
中位・下位の順位が改善しても選抜の結果は1ミリも動かない。
**選抜タスクの評価指標は、選んだ結果の実現値でなければならない。**

（なお ρ そのものは、サロゲート改良——目的関数や状態モデルの修正——の指標としては
正しく機能した。`ROLLOUT_SETTLE` は ρ 0.27→0.49 と実スコアが一致して動いた。
**同じ量が、用途によって正しい指標にも誤った指標にもなる。**）

### 診断: 較正された課題の外で計測器を使った

`twin.py` は**「1配置が崩れるか」という二値判定**用に較正され、実崩落 12/12 検出という
精度を持つ。しかし**30〜40手のエピソード全体の軌跡を再現する用途では検証されていない**。
1手ごとの小さなずれが積み上がる。settle 80 → 300 で ρ が 0.246 → 0.444 と大きく動いた
（＝整定の浅さが実際に穴だった）ことが、この読みを裏づける。残りの穴の候補は
`start_z` からの落下を模していないこと。

**裏返しの教訓**: 安いロールアウトが物理より良い選抜器なのは、
**重要なのが物理への忠実度ではなくエージェント自身の意思決定への忠実度**だから。
`ROLLOUT_SETTLE` が効いたのは、ロールアウトの**状態**を policy が見るものに一致させたため。
物理を足すと、別種の誤差が入る。
