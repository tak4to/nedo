## 時系列

### Day 1 (2026-08-29): 分析 → v1 → 原因究明 → v2

**1. シミュレータの厳密仕様を解読**（§2）

`src/ground_handling/validator.py` を読み、実機で検証。以下が判明：

- 判定は**完全に決定論的な幾何計算**。エージェント側で厳密再現できる → 実行可能性オラクルという設計の根拠。
- **1手でも配置NGが出るとエピソード即終了**。密度より完走率が支配的。
- 荷物は**7種類の固定カタログ**のみ（`configs/item_params.xlsx`）。
- fill_score の理論上限は約65点（全荷物体積 2.60 m³ / 有効容積 4.007 m³）。

実機検証で見つけた「罠」（`nedo-sim-hidden-traps` にも記録）：

- **縦積みは隙間ゼロで可能**（経路は最終高さの8cm上を通り着地接触は未判定）。一方 X隣接・Y前後は1.5cm超の隙間が必須。
- **底面zが [棚上面, 棚上面+0.05] に入る積み荷は即死**（持ち上げ量が0になり真下の支持荷物と衝突）。
- 扉は左側が `cut_x` 分狭く、左端が-0.51より左はX方向スライドで搬入される。
- 整定ドリフト 1〜1.6cm。**設計値ではなく観測姿勢で再計画しないと失敗する**。
- `env.step` は `0.012 + 0.015 × 積載数` 秒 → 8秒予算内に物理検証を10回以上回せる。

**2. v1 実装**（§9）

3層アーキテクチャ: `geometry.py`（オラクル）/ `packer.py`（候補生成+スコア）/ `agent.py`（IF）。
結果は `status: success` だが**課題000で41個中18個(44%)、課題001で42個中16個(38%)しか積めず早期終了**。

**3. 低スコアの原因究明**（§10） ← このセッション最大の成果

実測で切り分けた結果、**独立した4つのバグ**が見つかった。

| # | 原因 | 実測した証拠 |
| --- | --- | --- |
| A-1 | 探索範囲の定義バグ（`x_lo`が左ノッチ帯を丸ごと除外、`y_lo`が壁の無い扉側にも`thickness`を減算） | **コンテナ体積の29%**を最初から探索対象外にしていた |
| A-2 | 候補検証を900件で打ち切り | 有効候補48件が存在するのに最初の有効候補が**ランク2376**。探索は「配置不能」と誤判定 |
| A-3 | 極点のみの候補生成が疎すぎる | 密グリッドでは**848件**の有効配置があるのに極点探索は**0件** |
| A-4 | 支持面を「同一高さの箱の集合」として列挙 → 断片化 | **19個の箱に対し支持レベルが20個**（全部バラバラで載せられる平面が無い）→ 落下着地点モデルに変更して解決 |

加えて、**床接地荷物が充填率に計上されない**問題を発見（§10.2）。`evaluator.calculate_fill_rate` が
8隅すべてに `inclusion_margin`(-0.005) 以上の内側クリアランスを要求するため、床に接した荷物は
底面隅が床平面と一致して除外される。**配置済み体積の28〜32%**がこれで失われていた。
物理的に床から5mm浮かせることはできないため解消不能。READMEには「評価時は検証時より緩い」
とあり本番では計上される可能性があるが、配布コードとは矛盾している。

**結果**: fill 14.9→30.2 (課題000)、8.8→17.3 (課題001)。

### Day 2 (2026-08-30): 評価基盤の整備 → 手法監査 → 本命の試行

**4. 7シーン評価ハーネスの構築**（§11.1）

サンプルconfigは1コンテナ・オフラインなし・棚なし・初期荷物なしの2パターンのみで、
本番で出題される構成（2コンテナ / 棚あり / 初期荷物あり / 優先コンテナ）を**一度もテストしていなかった**。
`scenegen.py` + `harness.py` を作成し、7シーン（A〜G）で評価する体制にした。

→ **クラッシュはゼロ**（全構成で `status: success`）。2コンテナの負荷分散も優先手荷物の
ルーティングも正常動作を確認。理論上限との比較で「貪欲法は理論上限の23%」と判明。

**5. bigfirst の確定**（§11.3）

**lookahead=40 のシーンGが lookahead=1+オフラインのシーンAに負けている**という異常を発見。
原因は位置ベースのスコアだけでは小さい荷物から消費され大物が行き場を失うこと。
荷物体積に比例したボーナス（`W_ITEM_VOL=3000`）を追加 → 7シーン合計 **103.2 → 122.2**。

**6. 最適化専門家へのレビュー依頼**（§11.2）

中心的主張「これは密度の問題ではなく到達可能性(reachability)の問題。探索を強化しても意味がない」は
実測（2cm密グリッドでも有効配置0件なのに容積75%が空）と整合し採用。

一方、**提案の一部はソースコードで裏取りした結果、誤りと判明**：

| 専門家の主張 | 検証結果 |
| --- | --- |
| 「マージンを詰めれば0.65m幅が3列入る」 | **誤り**。外寸2.0mで計算していたが**内寸は1.92m**。0.65×3=1.95で最小マージンでも入らない |
| 「行内は外側X→扉Xの順に埋めるべき」 | **誤り**。荷物は**自分自身の目標X**から進入する（`rel_x = clip(target_x, ...)`）。X方向の共有廊下は存在しない |
| 「配置不能な荷物をスキップできるか要確認」 | できない。全失敗経路が `terminated = True` |

→ **外部レビューは有用だが、検証可能な主張は必ず自分で裏を取る必要がある。**

**7. 実験手法そのものの監査**（§12） ← 方法論上の最大の発見

方法論に特化した第三者レビューを受け、**測定基盤自体にバグがある**ことが判明した。

`choose_action` が「残り時間 ÷ 候補数」で壁時計の締切を配分しており、**CPU負荷次第で
結果が変わる**。実測：同一設定を並列実行しただけでシーンEが fill 18.2 vs 18.8 とずれた。

→ 研究用に**決定論的な作業予算**（`MAX_VALIDATIONS` カウンタのみ）で走る `research` モードを
`harness2.py` に追加。並列負荷下でも完全一致することを確認。本番相当の `production` モードは
**品質比較には使わず、タイミングのpass/fail検証専用**に分離。

この分離で追加の発見：**無制限予算でも平均27.8%にしかならない**（本番8秒制限下で27.3%）。
つまり**時間切れは主犯ではない**ことが数値で確定した。

同時に手法を是正：
- スコアを**理論上限で正規化**（`norm%`）し、平均と最小の両方を報告（合計だと高上限シーンが支配する）
- **devプール16シーン**を追加（A〜Gは既にbigfirstの採否に使われており「汚染」されているため）
- **`irace` は不採用**と判断（7シーンは母集団からのサンプルではなく手作りの固定シーン。7回評価すれば全部見終えており統計的早期打ち切りの前提が成立しない）

**8. 文献調査**（§12.1）

- 自作のスコア式（奥→低→左優先）は **Deepest-Bottom-Left-Fill (DBLF)** という確立手法と一致していた（独自に再発見していた）。
- 断片化解消の本命は **George & Robinson (1980) の wall-building**（Y方向の壁を奥から手前へ、壁内はZ方向の層を下から上へ）。40年以上の検証実績。

**9. optimize の GRASP 多スタート化**（§12.6）

予算に余裕がある（締切ヒット0回）ことを確認した上で、固定4ヒューリスティクスに加えて
ランダム重みの試行を残り予算分だけ追加する実装に拡張。

→ **A・D・devプールの計3シーンで検証したが、試行回数が6〜7倍になったにもかかわらず
旧コードと完全に同一の結果**。安全設計（既存解より厳密に良い場合のみ採用）なので残したが
効果は未実証。

この負の結果に診断的価値がある：**詰まりの原因は「投入順序」ではなく「配置ロジックの形」**
という仮説を補強した。

**10. 本命: wall-building 構造の実装**（§13）

| 版 | 内容 | 結果 |
| --- | --- | --- |
| v1（純粋制限） | Y候補を壁の背面エッジのみに制限 | **悪化** (fill 22.9→19.3)。壁の奥行きに満たない荷物が背面フラッシュにしか置けず手前が死ぬ |
| （バグ） | 静的な棚（Y方向は容器ほぼ全幅）が壁クラスタリングに混入 | **fill 0**（何も置けない）。即発見・修正 |
| v2（ハイブリッド） | 従来候補に壁候補を**追加**する形に変更 | 基準値に復帰、退行なし |
| v2+壁ローカルレベルマッチ | 同じ壁の中で高さを揃えるボーナス（前回失敗したグローバル版と違い壁単位にスコープ） | Bで**+21%**だが D -9%、E **-29%** → **全体で悪化** (27.8%→26.5%) |

→ **採用見送り**。`W_LEVEL_MATCH=0.0` に戻した。壁候補生成のインフラ自体は
「既存候補への追加のみ」で中立（実測で基準値と完全一致）なので温存。

途中、`TOP_TOL`（支持面クラスタリング用）を高さマッチにも流用していたため
効果が全く出ないバグがあり、`WALL_HEIGHT_TOL` として分離した。

**ほぼ全部が最初の失敗より後**にあった（45荷物の rollout 6.6秒のうち失敗前は 0.0秒、

無くなると全候補＋グリッド2段を舐めてから失敗を返すため。失敗で打ち切ると rollout が
**10〜30倍安く**なり、180秒あたりの試行数が約10回から数百回になった。
これが無いと LNS ループは1度も回らない。

あわせて rollout の失敗判定を policy に合わせた（`relax=True` での再試行を追加）。
これが無いと rollout は実際には死なない局面を「失敗」と数え、目的関数がズレる。

### Day 4 (2026-09-01): 真のボトルネックは「計算資源の配分」だった

**この日の結論: 詰まりの原因は積付ヒューリスティクスではなく、`choose_action` の予算配分バグだった。**
dev 32シーン **28.68 → 31.66**、ホールドアウト 32シーン **30.65 → 32.92**、積載率 42% → 46%。

#### 診断の連鎖（ここが本体）

1. **`tools/diag_void.py`**: 終了時のコンテナを 5cm ボクセルで解析。
   スカイライン下の占有率は **85〜93%** で、空きのほぼ全部が
   **スカイラインより上のヘッドルーム（1.0〜2.0 m³）**だった。
   → 「隙間を減らす」方向（下記の waste ペナルティ）は的外れ。詰まりは「上に積めない」こと。
2. **`tools/diag_cause.py`**: P00 の詰まり局面を 3cm グリッドで全探索すると
   **13543 件（6.8%）が受理される**。にもかかわらずエピソードは
   `is_valid=False`（探索が候補を出せず自死）で終わっていた。
3. **`tools/diag_gap.py`**: その局面で `choose_action` に 20秒与えると
   **4通りの設定すべてで placement が見つかる**。本番の 3.5秒では見つからない。
4. **`tools/diag_prof.py`**: `best_placement` 1回は半分埋まったコンテナで **0.25〜0.35秒**。
   一方 `choose_action` は予算を `(pool×containers)` で**均等割り**していたので、
   `look_ahead=20` では 3.5秒 ÷ 18 = **0.19秒/回**。全部タイムアウトして None を返す。
5. **決定的な確認**: 同じコードに policy 予算 15秒を与えると **+2.78 norm**。
   → 計算資源が律速であることが確定。

**`look_ahead>1` のシーンでプールが k=1 より悪くなることがある**という
[`SURVEY.md`](SURVEY.md) §1 の未解決の謎も、これで説明がつく。
プールが大きいほど1回あたりの探索時間が短くなるので、**選択肢が増えるほど探索が浅くなる**。

#### 採用（2件）

### Day 4b (2026-09-01): `SUPPORT_LIFT < GAP` — 5mm の定数バグ

LB 27.27 → 33 を確認したのち、プローブの指示通り**大プール専用のシーンプール**

#### 症状 → 原因

`scenes_k.json` の K03 は**9個置いた時点で死ぬ**。20秒与えても置き場所が見つからない。
`diag_state.py` で中身を見ると、**コンテナの奥半分（棚のある側）が完全に空**で、
手前半分だけに3段の塔が建っていた。

`packer.SUPPORT_LIFT = 0.017` に対し `geometry.GAP = 0.022`。

`geometry.resting_eff_start_z` は、底面zが**床面または棚面の +0.05 以内**にあるとき
8cm の搬入リフトを 0 にする。リフトが 0 だと掃引は荷物自身の高さを通るので、
**支持面との距離は持ち上げ量そのもの**になる。`check_transport_path` は `GAP` 以下の接近を
衝突と判定する。したがって **持ち上げ量 ≤ GAP の配置は例外なく不正**。

`diag_shelf.py` で詰まり局面を直接叩いた結果:

| `SUPPORT_LIFT` | 棚上の有効配置 |
| --- | --- |
| 0.017（当時） | **0 / 187** |
| 0.030 以上 | 40 / 187 |

これが黙って消していたもの:
- `require_shelf` コンテナの**棚面まるごと**
- **全コンテナに存在する**ノッチ側の小棚（`require_shelf=False` でも `static_boxes` に必ずある）
- 上面がたまたま棚平面の危険帯 [0.845, 0.895] に入った**荷物の上**

### Day 4c (2026-09-02): fill を上げる施策の総当たり — 全滅、ただし構造が判明

`SUPPORT_LIFT` 修正後の状態から「fill をさらに上げる」ための施策を7件測って、**7件とも中立〜悪化**。
ただしその過程で **fill_score の構造**が判明し、以後の方針が変わった。

#### 判明した構造: 置いた体積の 27% は原理的に計上されない

公式の `fill_score` は `evaluator.calculate_fill_rate` が `validator.inclusion_margin = -0.005`
で計算する（`env.py:51`）。**厳しい方**である。8個の角すべてが全平面から 5mm 内側にないと
その荷物は体積に**一切**加算されない。

`tools/diag_incl.py` で棄却理由を平面ごとに分解した結果:

| 平面 | 法線 | 棄却された荷物 | 置いた体積に占める割合 |
| --- | --- | --- | --- |
| 0（**床**） | (0,0,-1) @ z=0.04 | 19個 | **21.2%** |
| 6（奥壁 +Y） | (0,1,0) | 5個 | 3.8% |
| 1（側壁 +X） | (1,0,0) | 2個 | 2.7% |

**床が支配的で、しかもこれは物理的に不可避**である。床の内包平面は
`z = thickness = 0.04` にあり、法線は下向き。内包条件は `dot <= -0.005` すなわち
**荷物の底面が z >= 0.045 にあること**。床に接地した荷物の底面は定義上ちょうど 0.04 なので、
`dot = 0 > -0.005` で必ず落ちる。実測でも**床接地19個中、計上されたのは0個**。
一方**何かの上に載った94個は87個が計上**された。

`FLOOR_LIFT = 0.02` で設計上は 0.06 に浮かせているが、整定で床まで落ちるので無意味。
→ **1層目は必ず捨て石になる。その価値は「2層目以降を持ち上げる台」としてのみ。**

#### この構造を利用しようとして失敗した施策

| 施策 | 結果 | なぜ負けたか |
| --- | --- | --- |
| 床には小さい荷物を回す（`choose_action` の `W_ITEM_VOL` を床配置で 0 / 負に） | **-2.12 / -2.82** | `bigfirst` は生存のための maximin 解。小物から消費すると大物の置き場が無くなり早死にする。計上の付け替えより完走の方が高い |
| 床配置だけ平坦性ペナルティを追加（1層目を薄くして上に多く積む） | -1.91 | 同上に近い。1層目の選択を歪めると後段が詰まる |
| 設計内包パッドを厚くしてドリフト流出を防ぐ（`pad` 0.015 / 0.020） | **-22.1 / -30.2** | 破滅的。使える空間を削る損失が、計上できる体積の増加を桁で上回る |
| 壁クリアランス 0.022 → 0.030 | +1.00 (se 1.46) | ノイズ内 |

**結論: 27% の未計上は採点規則の構造的な性質であり、買い戻そうとすると必ず割に合わない。**
全参加者が同じ規則の下にいる。**fill を上げる道は「計上率の改善」ではなく「積む個数」だけ。**

2. **devプールでスクリーニング → A〜Gで最終確認**（一部シーンの改善だけで採用しない）
3. **`norm%` の平均と最小の両方を見る**（合計は高上限シーンが支配する）
4. **「予算を使い切れているか」を先に確認**してから予算追加系の改善を検討する
5. **品質とコストを別軸で見る**（品質横ばいでコストだけ増える変更は改善以下）
