# スコア向上のための学習プラン（2026-09-03）

## 0. 何を学習するか — 方策そのものではなく「スコア関数の重み」

現行エージェントの方策は、実は**すでに線形モデル**である。

```
配置スコア = W_BACK·y_back − W_LOW·bottom − W_FLAT·fz − W_LEFT·x_left − W_MASS_HIGH·mass·bottom
荷物選択   = 配置スコア + W_ITEM_VOL·volume + priority_bonus
```

つまり「学習させる」とは、**この重みベクトルを目的関数に対して当てはめること**である。
そして決定的な事実として:

> **これらの重みは全て `fill` と生存のために手で調整されたもので、
> 真の目的関数（5指標の合成値＋閾値）に対しては一度も調整されていない。**

ここが最も大きく、かつ確実な学習の余地である。

### なぜ Q学習ではないのか

| 論点 | Q学習 | 直接方策探索（CEM/ES） |
| --- | --- | --- |
| 報酬が階段関数で平坦域が広い | 勾配が無く信用割当が破綻 | **そのまま扱える**（目的値を直接評価するだけ） |
| 終端報酬1個・40手 | 最悪の設定 | 無関係（エピソード単位で評価） |
| 1エピソード10〜30秒 | 10⁴〜10⁵回必要＝100〜1000時間 | **160回程度で足りる＝約10時間** |
| PyTorch が無い | numpy でMLP自作＋提出リスク | **重み7〜13個を定数として同梱するだけ** |
| 実行可能性の学習 | DRLの主目的だが我々は厳密オラクルを保有 | 不要 |

**問題の構造（少パラメータ・高コスト評価・微分不可能・階段状の目的関数）に対して、
CEM は教科書的に正しい選択であり、Q学習は教科書的に誤った選択である。**

## 1. 目的関数の定義（ここを間違えると全部無駄になる）

合成値だけを目的にすると「積まない」ことでゲームされる
（`SUPPORT_MIN_COVER=1.0` は合成値 60.7 だが積載率 31.7% で閾値割れ＝実際は fill のみの 13.6）。
そこで**閾値モデルの推定LB**を目的関数にする。

```
score(scene)  = composite(scene)        if packed% >= TH
              = fill(scene)             otherwise
objective     = mean over TH in {40, 46, 50} of  mean over scenes of score(scene)
```

閾値の正確な位置は不明なので、**3つの閾値の平均**を取って位置に対して頑健にする。
これにより「積載率を保ちながら合成値を上げる」が自動的に目的化される。

## 2. Phase 1 — 特徴量の拡張（学習の前に、動かせる自由度を増やす）

**現状の5特徴量は粗すぎる。** 重みだけ最適化しても届く範囲が狭い
（安全域の全設定で合成値の幅はわずか 3.4）。

そこで、**個別にテストして落ちた／未着手のアイデアを、独立した施策としてではなく
「特徴量」としてまとめて投入し、重みは学習に決めさせる。**

| 特徴量 | 根拠 | 実装 |
| --- | --- | --- |
| `waste`（footprint下の平均空隙深さ） | 内部空隙が 0.39〜1.31 m³ に増えた（§課題分析 §6） | 実装済み `patches.py:_mk_waste`、SATで O(1) |
| `support_ratio`（直下の被覆率） | `_footprint_supported` の hit/total を再利用 | 既存計算の副産物 |
| `wall_contact`（左右奥壁への接触数） | 壁に接すれば横滑りが止まる＝stability | O(1) |
| `seam_offset`（直下の箱の縁とのズレ＝インターロック） | extreme point 生成は継ぎ目が揃いやすい構造的欠点 | landing_index から O(k) |
| `ceiling_gap`（天井までの残り） | 最上層が拘束されていない（最上面1.48/天井1.57） | O(1) |
| `skyline_delta`（配置によるスカイライン粗さの変化） | 粗さが詰まりの主因 | SATで O(1) |
| `is_soft` / `is_prio`（荷物選択側） | soft/placement は積むほど下がる | O(1) |

**この設計の要点**: 本セッションで単独テストしたヒューリスティクスは **0勝23敗**だった。
しかしそれらは「他の重みを固定したまま1項だけ足す」形の検証である。
**複数項を同時に動かせば到達できる点が、1項ずつでは到達できない**のは
最適化として当たり前であり、23連敗はその仮説と矛盾しない。

計算コストは問題にならない。**予算を3倍にしても +0.07** しか動かない＝
探索時間は既に飽和しており、特徴量計算に回す余地がある。

## 3. Phase 2 — CEM による重み最適化

```
パラメータ  : 既存7 + 新規7 = 約13次元（対数スケールで扱う）
個体数      : 24 / 世代
エリート    : 上位25%（6個体）
世代数      : 8〜12
評価        : dev 32シーン、全個体で同一シーン（common random numbers）
1評価       : 約220秒（14並列）
総コスト    : 24 × 10 = 240評価 ≒ 15時間（夜間バッチ1回）
```

**分散低減**: 全個体を同じシーン集合で評価する（common random numbers）。
同一コード3回の反復で32シーン平均の sd は 0.04 と測定済みなので、
狙う効果量（0.5〜3）に対して十分小さい。

**枝刈り**: 16シーンで粗く評価 → 上位半分だけ32シーンで再評価、で約半分のコストにできる。

## 4. Phase 3 — 過学習の検証（ここを省くと意味が無い）

CEM は 32シーンに対する最適化なので、**必ず3段で確認する**。

1. **別seedのホールドアウト32シーン** — 効果が半分以下に落ちるなら過学習
2. **`tools/scenes_real.json`（実タスク R000/R001）** — 決定論的に再現するので1回で判定できる
3. **セグメント別**（棚あり/なし、コンテナ1台/2台、look_ahead別）— 一部セグメントの犠牲で平均を上げていないか

**本セッションの教訓**: 棚下候補は合成64シーンで積載率+9と大勝したが、
実タスクでは 64.3%→54.8% と逆符号だった。**合成プールだけの検証は信用できない。**

## 5. Phase 4（任意・Phase 3 の結果次第）— 終端価値の教師あり回帰

Phase 2 が飽和したら、次は**1手先読みの終端価値**を学習する。

- **教師データ**: CEM の過程で走る数千エピソードをそのまま使う（追加コストゼロ）
- **入力**: 状態特徴量（スカイライン統計・残り空き体積・置ける荷物型の数・積載ペース）
- **出力**: 終端の推定LB
- **モデル**: 線形 or 隠れ層1つの小さなMLP。**numpy で実装し重みを定数として同梱**
- **使い方**: 上位M候補について、配置後の状態特徴量を評価して選び直す

Q学習と違い**ブートストラップが無い**ので、サンプル効率が桁違いに良く、
発散もしない。`docs/GAMEPLAN.md` §4.2B に同趣旨の記載がある。

**注意**: 過去に「生存指標での re-rank」は失敗している（信号が崖まで平坦）。
違いは、あれが**手作りの指標**だったのに対しこちらは**回帰で当てはめる**点。
それでも失敗する可能性は十分あるので、Phase 2 の後に判断する。

## 6. 期待値の見積もり（正直に）

| Phase | 期待値 | 確度 |
| --- | --- | --- |
| Phase 2（既存7重みのみ） | **+1 〜 +2** | 高。目的関数に対して未調整なので下限は0ではない |
| Phase 2（特徴量13個） | **+2 〜 +5** | 中。到達可能集合が広がるが保証はない |
| Phase 3 で生き残る割合 | 半分程度を見込む | 過学習は必ず起きる |
| Phase 4 | +0 〜 +3 | 低。類似の手法が過去に失敗している |

**上振れの本命は閾値の崖**である。現在プールごとに 2〜11シーンが閾値未満で、
1シーン跨がせるごとに約 +25/シーン数。CEM の目的関数はこれを直接織り込んでいるので、
「合成値を少し下げてでも積載率を上げて崖を越える」解を自力で見つける可能性がある。
**手作業では絶対に見つけられない種類の解**であり、ここが学習を入れる最大の理由である。

## 9. Phase 2 の結果（base7、2026-09-05）— **明確な負の結果。採用せず**

8世代 × 14個体 × 32シーン、4.76時間で完走。

| | 訓練プール | 未使用4プール平均 |
| --- | --- | --- |
| Δobjective（最良個体） | **+3.50** | **−0.87** |
| Δobjective（分布平均） | +0.34 | **−0.47** |
| Δcomposite（分布平均） | −0.66 | −0.27 |

未使用プールは `scenes_k` / `scenes_ktest` / `scenes_shelf` / `scenes_shelftest`（訓練は `scenes_pool` のみ）。
実タスクは R000 合成値 54.7→61.8 だが R001 は 55.0→45.7（R001 は不安定シーンなので判断材料にしない）。

**最良個体が訓練 +3.50 / 未使用 −0.87、分布平均が訓練わずか +0.34 という差は、
勝者の呪いの典型的な署名である。**

### 原因（定量的に特定）

崖の近傍（積載率 40〜52%）にいるのは **32シーン中わずか6件**で、
**1件が崖を跨ぐと目的値が 0.67 動く**。訓練で得た +3.50 は、
**その6件のうち約5件を跨がせたのと同じ大きさ**である。

→ CEM は方策を改善したのではなく、**訓練セットのどのシーンが境界上にあるかを記憶した。**
階段関数を直接最適化した時点でこの結末は必然だった。目的関数の設計ミスである。

### もう一つの、より重要な結論

**分布平均でも composite が動かなかった（訓練 −0.66 / 未使用 −0.27）。**

Phase 1 の前提「既存の重みは fill と生存のために調整されており、
合成値に対しては未調整だから伸び代がある」は**否定された**。
安全域の全設定で合成値の幅が 3.4 しかないという以前の観察と一致しており、
**既存7重みの周辺では合成値の地形は本当に平坦**である。

→ **学習路線に残された望みは新特徴量（full14）だけで、既存重みの再調整ではない。**

### 実施した修正

| # | 修正 | 内容 |
| --- | --- | --- |
| 1 | `objective.smooth_objective` | 階段をロジスティックの傾斜に置換（中心46%・幅6%）。誘因は保ったまま、1シーンが 0.67 を持つ不連続を除去。シーン別 sd 11.1 → 8.7 |
| 2 | `cem.py --scenes a.json,b.json` | 複数プールを1つの訓練集合に結合できるようにした。32シーン→96シーンで過学習の余地を減らす |
| 3 | `cem.py` は既定で smooth を使う | 階段版は `--step-objective` で明示的に選ぶ（過学習することを docstring に明記） |

### 見積もりの誤り（記録）

私は Phase 2（既存7重みのみ）を「**+1〜+2、確度は高い**」と見積もった。
実測は **未使用プールで −0.47〜−0.87** だった。誤りの原因は2つ:

1. 目的関数の分散を見積もらずに「目的関数に未調整だから下限は0ではない」と考えた
2. 単一プール32シーンで7次元 × 112評価という設定の過学習リスクを過小評価した

**次に見積もりを出すときは、まず目的関数の1シーンあたり感度を測ること。**

### 得られた作業原則

**新しい判断基準を思いついたら、単独A/Bで却下する前に、
`packer.py` に重み0の特徴量として追加して CEM に入れる。**
単独A/Bは (a) 他の重みがその項の存在を前提に調整されていない、
(b) 32シーンでは +1.0 を検出力20%でしか捉えられない、の二重の理由で
「効果が無い」と「見えない」を区別できない。
